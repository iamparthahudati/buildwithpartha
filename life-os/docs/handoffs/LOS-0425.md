## Completed behavior

Adds `FormDialog` to `components/feedback/` — a create/edit form composed on `Dialog` (LOS-0412), reusing the exact `pending`/`error` caller-controlled shape `ConfirmDialog` (LOS-0413) already established.

### One `onClose` funnel is what makes the dirty guard possible

`Dialog` already funnels Escape, the backdrop and its own close button into a single `onClose` callback. `FormDialog` adds a `requestClose` wrapper around that same funnel: while `pending`, every dismissal path is a no-op; while `isDirty`, every path opens a `ConfirmDialog` ("Discard unsaved changes?") instead of closing directly. Cancel calls the same `requestClose`, so all four dismissal paths — Escape, backdrop, the header's close button and Cancel — share one guard rather than four separately-wired ones, the same reasoning `Drawer`'s (LOS-0414) own dirty guard used.

### No internal try/catch — `pending`/`error` stay the caller's

Identical to `ConfirmDialog`'s split: `FormDialog` has no async code of its own. `onSubmit` is called once, synchronously, only when not already `pending`; the caller's own submit handler owns the request, sets `pending` while in flight, and sets `error` on failure. A successful submit needs no special-case code in `FormDialog` at all — the caller calls the same `onClose` it was given, and `Dialog`'s existing focus trap already restores focus to whatever opened it.

### Mobile: a true full-screen sheet, not `Dialog`'s baseline bottom sheet

`Dialog` already has its own mobile treatment below 480px (a bottom sheet capped at 90dvh, sized for a short confirmation). A real form usually needs the whole viewport once its own on-screen keyboard is up, so `form-dialog.css` adds a second, wider breakpoint (`width < 768px`) that lifts `.lifeos-form-dialog` out of the backdrop's centering layout via `position: fixed; inset: 0`, filling the viewport with no rounded corners.

Getting this fully correct took two passes, both caught live in a browser rather than by any automated test (jsdom has no layout engine):

1. **The dialog wasn't actually full-screen.** The mobile rule set `width: auto` so `inset: 0` could stretch it horizontally, but never set `height: auto` — so the native `<dialog>` UA default (`height: fit-content`) won, and the "full-screen sheet" was really a small box vertically centered by the UA's default `margin: auto`. Fix: add `height: auto` alongside `width: auto`.
2. **Fixing that exposed a second bug.** `Dialog`'s shared `.lifeos-dialog` is `display: grid` with implicit auto rows and no `grid-template-rows`; once the container was correctly stretched to the full viewport height, the grid's auto rows absorbed the leftover space by spreading themselves apart — header, description and the form's fields/actions pulled apart by large empty gaps instead of the fields scrolling in a contained area. Fixed by switching `.lifeos-form-dialog` specifically (not the shared `Dialog`, so no other consumer is affected) to a flex column below 768px: header/description keep their natural size, `.lifeos-dialog__body` and the `<form>` inside it become `flex: 1`, and `.lifeos-form-dialog__fields` is the one scrollable region — so the actions row stays pinned to the bottom edge instead of floating mid-screen.

Both were confirmed by reading `getComputedStyle(dialog).height` against the real viewport height, not just by eyeballing a screenshot.

## Known limitations or follow-ups

- No built-in multi-step/wizard mode — a single `children` slot is one step's worth of fields, matching every other composed form field in this epic (`DateRangeField`, `DateTimeField`, etc.) rather than something FormDialog was asked to support.
- The discard confirmation's copy (`discardTitle`/`discardDescription`/`discardConfirmLabel`) has defaults but is fully overridable; no caller has yet exercised a custom string, so that path is untested beyond the default.
