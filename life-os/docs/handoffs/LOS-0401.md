## Completed behavior

First ticket of Epic 04, built on the atom API frozen at LOS-0333. Adds `apps/web/src/components/forms/`: `FormField`, `FormFieldGroup`, `FormErrorSummary`, the `useFormFieldRegistration` hook, and a `lib/serverErrors.ts` helper for mapping backend field-validation responses.

### FormField is a render prop, not a clone

The obvious implementation — `FormField` clones a single child element with a generated `id`/`label`/`error` — does not typecheck. Every LifeOS atom requires its own `label` as a real, non-optional string (the same safety net `IconButton`'s required `label` uses, LOS-0307), and TypeScript checks `<TextInput />` against `TextInputProps` at the point it is written, before it ever reaches `FormField`. A clone-based `FormField` would force every caller to invent a throwaway label just to compile — which is exactly the kind of decorative, defeatable requirement the atoms were built to prevent.

`FormField` instead hands back a `FormFieldRenderProps` object (`id`, `label`, `required`, `description?`, `error?`) through its `children` function:

```tsx
<FormField name="title" label="Task title" error={titleError}>
  {(field) => <TextInput {...field} value={title} onChange={(e) => setTitle(e.target.value)} />}
</FormField>
```

Every prop the caller spreads is real and checked. `required` is handed back rather than applied automatically, because it means something different on different atoms — a required text field must not be empty, a required checkbox means the box must be checked, which is right for very few checkboxes — so the caller decides whether to forward it to the specific control they chose.

`RadioGroup` does not fit this shape (it names its label `legend`, and does not accept an external `id`) and is explicitly out of scope for `FormField`; a form using it registers directly with `useFormFieldRegistration`, tested in `FormField.test.tsx`.

### Error-summary linkage

`FormFieldGroup` wraps one form's fields; any `FormField` inside it registers its current id/label/error through a stable context (split into a write side and a read side, so a field's own registration effect never re-runs because a sibling's error changed). `FormErrorSummary`, placed wherever the form wants it, lists every currently-registered error as a button that moves keyboard focus to the field and scrolls it into view.

Per `docs/30-CONTENT-AND-TONE-GUIDE.md`, the summary must appear and take focus **only after a failed submit**, never during normal typing. `FormErrorSummary` does not decide that timing itself — it renders nothing when there is nothing to show, and exposes a forwarded ref so the form's own submit handler calls `.focus()` at the moment it actually knows the submit failed. `tabIndex={-1}` makes it a valid target without adding a stray tab stop, the same pattern the skip link already uses for the main landmark.

Both the summary and every inline field error use `role="alert"`, so the summary carries its own `aria-labelledby` pointing at its heading — without it, an assistive-technology query for "the alert" cannot tell the summary apart from any one field's own alert.

### Server-error mapping

`docs/05-API-CONVENTIONS.md` fixes the shape a failed validation returns: `errors: [{ field, code }]` — a stable code, never a final sentence, because the same code means a different approved message on different fields. `lib/serverErrors.ts`'s `groupFieldProblems` turns that array into a `Record<fieldName, code>`, keeping the first violation per field (the earliest is normally the most fundamental — a required check before a length check). Turning a code into copy stays the caller's job, using the tables in the tone guide; `FormField`'s own `error` prop already accepts a plain resolved string from either source.

## Known limitations or follow-ups

- `FormFieldGroup`/`FormErrorSummary` do not themselves know when a submit has failed; the calling form decides when to render the summary and when to call its forwarded `.focus()`. This is intentional — submission timing is feature-specific — but is worth restating for whoever builds the first real create/edit dialog (LOS-0425) so the pattern is not reinvented.
- `groupFieldProblems` returns codes, not messages, by design; no code-to-message table exists yet. The first feature that consumes a real server validation error is where that per-field table should first appear, scoped to its own fields per the tone guide rather than as a global dictionary.
- `RadioGroup` composition with the error summary was proven with a stand-in, not with `RadioGroup` itself, since no screen yet has a `RadioGroup` inside a form needing summary linkage.
