## Completed behavior

Added the frontend's typed API client, in-memory session store and route guard on top of LOS-0505/LOS-0506's login/logout API — the first frontend ticket to call the backend at all.

- `@tanstack/react-query` (`5.101.4`) is added as a new direct dependency, fulfilling `02-ARCHITECTURE.md`'s existing "TanStack Query owns server state and caching" rule rather than deciding something new (the same kind of addition LOS-0304 made for `lucide-react`, recorded there in ADR-013 because *which* icon set was a real decision — no ADR is needed here since the architecture already named the library, this ticket only provisions it). `app/queryClient.ts` is the one `QueryClient` instance; no domain query/mutation hooks exist yet, so its `defaultOptions` (one query retry, no mutation retries) are a documented engineering default for later tickets to inherit or override.
- `lib/apiClient.ts` is the one `fetch` wrapper every feature's API module calls through: same-origin credentials (`credentials: "same-origin"`, never a bearer token read from any browser storage), automatic `X-CSRF-TOKEN` attachment on `POST`/`PUT`/`PATCH`/`DELETE` once a token is known, and a single `401` `AUTHENTICATION_REQUIRED` check that reports through a configured callback — never for a `login`/`signup` endpoint's own `401 INVALID_CREDENTIALS`, which is a different, unrelated failure. `configureApiClient` is a plain module-level setter rather than an `@state` import: `lib/` stays a leaf with no dependency on application state, and `state/AuthSessionProvider` wires itself in once, from a mount effect.
- `state/authSession.ts` + `state/AuthSessionProvider.tsx` hold the current user and CSRF token **in memory only** — the ticket's "no browser token storage" line, proven by a test asserting `Storage.prototype.setItem` is never called across a full set/clear session cycle. Split into a context/hook file and a component file for exactly the reason `toastQueue.ts`/`ToastProvider.tsx` already are: `eslint-plugin-react-hooks`' `react-refresh/only-export-components` rule would otherwise flag a `.tsx` file exporting both a component and a hook. `AuthSessionProvider` calls `useQueryClient()` directly (must be mounted under `QueryClientProvider`) and clears the entire cache in two places: `clearSession` (logout, 401 recovery) and `setSession` when the incoming user's `id` differs from whoever was previously signed in (an account switch with no intervening logout) — refreshing the *same* account's session (a token rotation) deliberately does not clear it, proven by a test asserting a same-account `setSession` leaves cached data alone.
- **401 recovery** (`23-NAVIGATION-AND-ROUTES.md`: "On 401 ... clear private query caches and go to login with a validated same-origin relative `returnTo`") lives in `AuthSessionProvider`'s `configureApiClient` wiring: on `AUTHENTICATION_REQUIRED`, it drops the session (which clears the cache), then navigates to `buildLoginPathWithReturnTo(currentPathForReturnTo())`. It no-ops if there was no signed-in user to begin with, so a background request racing an already-handled 401 cannot navigate twice or throw against a state that is already logged out.
- `lib/returnPath.ts` is the "return-to validation" the ticket names: `isSafeReturnPath` is a type predicate that rejects anything not a root-relative, control-character-free, same-`window.location.origin` path nested under the app's own `VITE_APP_BASE_PATH` — a leading `//` or `/\`, an embedded `://`, or a path merely string-prefixed by (not nested under) the app segment (`/life-os-imposter/...`) are all rejected, closing the open-redirect shape `?returnTo=https://evil.example` or `?returnTo=//evil.example` would otherwise exploit. `resolveReturnTarget` (for LOS-0510's login screen to call) decodes, validates and falls back to Today for anything missing, unsafe, or pointing at the login page itself — never back to login, which would leave the user looking signed in but going nowhere.
- `features/auth/components/RequireAuth.tsx` is the route guard component: built directly on `window.location`/`history`, not a router, since none is wired into LifeOS yet (`useDeepLinkParam`'s own docstring records the same state, and `LOS-0603` — "Build application shell ... protected routing" — is explicitly where a real router will compose this). It renders nothing while `user` is `null` (no flash of protected content) and redirects to `buildLoginPathWithReturnTo(currentPathForReturnTo())` from an effect; `23-NAVIGATION-AND-ROUTES.md`'s own line is quoted directly in its docstring: "client guards improve UX but are not authorization" — every protected endpoint still enforces its own session check server-side regardless of this component.
- `features/auth/api/authApi.ts` is the typed auth API client: `signup`/`verifyEmail`/`login`/`logout`/`logoutAll`, request/response shapes copied field-for-field from `SignupRequest`/`LoginRequest`/`VerifyEmailRequest`/each `*Response` record. `features/auth/hooks/useLogin.ts` and `useLogout.ts` wrap `authApi` with `useMutation`, ready for LOS-0510's login screen and a future account-menu "sign out" action: `useLogin`'s `onSuccess` destructures `LoginResponse` and deliberately excludes `csrfToken` from the stored `AuthUser` object (kept as the session's separate `csrfToken` field), so the one-time bootstrap value never ends up in a spot other code reads for display. `useLogout` accepts an `allDevices` option (`/auth/logout-all`) and an injectable `navigate` (defaults to `window.location.assign`), and leaves the session untouched on a rejected request (LOS-0506: a mismatched CSRF header, `403`) rather than optimistically clearing it.

## Known limitations or follow-ups

- **No `GET /auth/session` or `/auth/me` endpoint exists** (LOS-0506's own handoff already flagged this ahead of this ticket). `05-API-CONVENTIONS.md` documents "`GET /auth/session` supplies the current safe user profile and CSRF bootstrap information" as though one exists, but no ticket in `EPIC-05-IDENTITY.md` builds it. Consequence: a full page reload always starts this frontend from `{ user: null, csrfToken: null }` even when the `HttpOnly` session cookie is still valid — there is no way to silently restore the in-memory user/CSRF token without one. The judgment call this ticket makes, per its own instructions, is to treat "no in-memory CSRF token" as logged out at the API-client layer and let `RequireAuth` redirect to login on the next protected render, rather than inventing a backend endpoint (a real one has a non-trivial security shape of its own — minting a fresh CSRF secret from a `GET` is not obviously safe by default). Building it, if wanted, should be its own reviewed identity ticket, not a side effect of this one.
- `useLogin`/`useLogout` are built and tested but have no UI caller yet — LOS-0510 ("Build login form and screen") is the ticket that wires a real form to `useLogin`, and a future account-menu/settings ticket (LOS-0415's `AccountMenu` already exists; LOS-0516 owns session management) is the eventual caller of `useLogout`.
- `AppProviders`/`RequireAuth` are complete and tested in isolation but not yet mounted anywhere real: `App.tsx` is still the LOS-0201 placeholder, and no router exists in the app yet. `LOS-0603` ("Build application shell ... protected routing") is where these compose into an actual page.
- `queryClient`'s `defaultOptions` (one retry for queries, none for mutations) are a documented engineering default, not a reviewed product requirement — no domain data-fetching hook exists yet to validate them against.
- `apiClient.ts`'s network-failure path (a `fetch` rejection reaching the `catch` block) is exercised by type but not by a dedicated test; every test drives it through a mocked `Response`, matching how the rest of this codebase tests HTTP-layer code.
