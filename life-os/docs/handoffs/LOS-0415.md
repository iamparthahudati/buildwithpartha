## Completed behavior

Adds `Menu` and `AccountMenu` to a new `apps/web/src/components/navigation/` category, plus a standalone pure function, `menuPosition.ts`.

### Menu is the ARIA menu-button pattern, built on real DOM focus

Each item is a real `<button role="menuitem">` inside `<li role="presentation">`, with a roving `tabIndex` — the currently active item gets `0`, every other item gets `-1` — so arrow keys move the platform's own focus rather than `aria-activedescendant` (the pattern `Combobox`, LOS-0403, uses for its own different reason: a combobox must keep real focus on its text input at all times, which a menu has no such constraint against). Opening the menu, by click or by `ArrowDown`/`ArrowUp` on the closed trigger, moves focus onto an item immediately rather than leaving it on the trigger — matching a native `<select>`'s own popup behavior, and confirmed in a live browser (see Validation below), not just in jsdom.

`ArrowDown`/`ArrowUp`/`Home`/`End` move among enabled items only, skipping disabled ones and wrapping at the ends. `Enter`/`Space` activates the focused item, closes the menu and returns focus to the trigger; `Escape` does the same without activating anything; `Tab` closes the menu without forcing focus anywhere, since a menu is not modal and Tab should carry focus on to whatever the page's own order says comes next.

### Typeahead cycles a repeated letter, rather than growing a literal search

A first version simply appended every typed character into one search buffer and matched it as a literal prefix. A test caught this immediately: typing the same letter twice (the standard way to cycle through several items starting with "d", the way a native `<select>` works) searched for an item starting with "dd" instead, found nothing, and did nothing. The fix special-cases a run of the identical character: the match text stays pinned to that single character while the search cursor keeps advancing past the currently active item, so repeated presses cycle Archive → Assign → Add to project → back to Archive. Typing distinct characters in succession still narrows a literal, growing search, matching the two behaviors real single-select typeahead needs.

### The trigger is cloned for id and ARIA wiring, not for a ref

`cloneElement` attaches `id`, `aria-haspopup="menu"`, `aria-expanded`, `aria-controls` and an `onClick`/`onKeyDown` toggle onto the caller's own trigger element without replacing any handler it already has — the same "wrap without replacing" approach `Tooltip` (LOS-0326) uses for its own trigger. Focus is restored to the trigger by `document.getElementById(triggerId)` — the same lookup this file already uses to focus the active menu item — rather than by forwarding a ref through `cloneElement`. That sidesteps requiring every possible trigger element to support ref forwarding, and also sidesteps a `react-hooks/refs` false positive: the ESLint rule flags any `ref` property passed through `cloneElement`'s props object as a possible synchronous ref read during render, regardless of how the ref-setting function itself is defined, because `cloneElement` is not recognized as JSX by its static analysis.

### Collision detection resolves side and align independently, against the real viewport

`menuPosition.ts` mirrors `tooltipPosition.ts`'s (LOS-0326) shape and reasoning — a pure function so collision rules are testable without a layout engine — but a menu popup is corner-anchored rather than centered, so it resolves two independent axes: `side` (drop below the trigger, preferring `bottom`, flipping to `top` only when that is genuinely better) and `align` (line up with the trigger's leading edge by default, flipping to the trailing edge only when the leading edge would overflow). Both axes are covered by table-driven pure-function tests, and the wiring itself — the component actually applying the resolved classes — was confirmed twice: once with a mocked `getBoundingClientRect` in Vitest, and once live in a real browser, where a catalog specimen sitting low enough on the page correctly flipped its popup above and to the trailing edge of its trigger rather than reporting a position that would have overflowed. That second check mattered: jsdom has no layout engine, so a wiring bug that only manifests against real measured dimensions could pass every unit test and still be broken in production.

### Dismissal listens for pointerdown, not blur — the touch-safe path

Clicking or tapping outside the open menu closes it via a `pointerdown` listener on `document`, checked against the menu's own root element, rather than a blur handler on the trigger or popup. A blur-based approach is the more common shortcut, but real touch taps on iOS Safari do not always blur the previously focused element the way a mouse click does, so a menu relying on blur can fail to dismiss on the exact input method most likely to tap outside it. This is the same reasoning class as `Drawer`'s pointerdown-based backdrop handling (LOS-0414), applied here to a menu with no backdrop at all.

### AccountMenu is a fixed shape on top of Menu, not a new pattern

`AccountMenu` composes `Menu` with an avatar trigger (name-only accessible label, since the button's own `aria-label` already covers it — no `standalone` prop needed) and a `header` slot showing a larger avatar, the person's name and, if given, their email. `items` stays exactly `Menu`'s own `MenuItemDescriptor[]` — profile/settings/sign-out and their copy are the caller's, matching the "never invent copy internally" rule this design system applies everywhere else (`EmptyState`, `ErrorState`, `ConfirmDialog`). Aligns to the trailing edge (`align="end"`) by default, since an account menu conventionally sits at the end of a top bar.

## Known limitations or follow-ups

- No submenu support — `MenuItemDescriptor` has no nested-items case. Nothing in this ticket's scope needs one; LOS-0426 (CommandPalette) is the next composed pattern likely to want grouped results, not nested menus.
- Only one menu is expected open at a time in practice, but nothing here enforces that globally the way `dialogStack.ts` enforces topmost-only Escape routing for `Dialog`/`Drawer`. Two independently triggered `Menu`s can be open simultaneously; this was judged acceptable since, unlike modals, an open dropdown menu does not block interaction with the rest of the page.
- `menu.css`'s popup has a fixed `min-width`/`max-width`, not derived from the trigger's own width — reasonable for an action menu, but a future component wanting a menu that matches its trigger's width (a `Select`-like popup) would need a new option, not reuse this one as-is.
