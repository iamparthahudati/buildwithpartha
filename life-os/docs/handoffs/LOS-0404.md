## Completed behavior

Adds `DateRangeField` to `apps/web/src/components/forms/`: two `DateInput`s (LOS-0318) grouped under one real `<fieldset>`/`<legend>`, the same pattern `RadioGroup` (LOS-0312) uses for a related group of native controls rather than a single one. A range is one concept made of two dates, not two unrelated fields that happen to sit next to each other.

### The order check needs no copy from the caller

`end` before `start` is invalid for every date range regardless of what the range means to a particular feature — unlike a required-field message, which genuinely differs per field, "choose an end date on or after the start date" is a universal rule. `DateRangeField` computes it itself with `compareLocalDates` and shows it automatically; a caller-supplied `error` (a server error, say) still takes priority over the built-in check, following the same precedence every other LifeOS field uses for combining client and server validation.

The check is also enforced structurally, not just announced: each side additionally constrains the other's native picker (`end`'s `min` becomes `start`, `start`'s `max` becomes `end`, layered with whatever `min`/`max` bounds the caller passed), so the browser's own date picker refuses the invalid choice as the user is making it, not only after they submit.

### Presets stay a mechanism, not a policy

`presets` is a prop — `{ label, range: (today) => DateRangeValue }` — rendered as a row of buttons; the component does not hard-code "This week" or any other business meaning into a shared primitive, the same reasoning `DataTable`'s ticket (LOS-0424) already states for domain columns. `buildCommonDateRangePresets()` ships a small ready-made set (Today, next 7 days, next 30 days) a caller can hand straight to `presets` or use as a starting point, but it lives in its own module (`dateRangePresets.ts`) rather than the component file — colocating a plain function with a component export breaks React Fast Refresh, the same reason `scales.ts`/`progress.ts`/`avatarIdentity.ts` already sit apart from their components.

Every preset is computed from `todayLocalDate(timeZone)` at the moment it is clicked, using the caller's confirmed IANA timezone rather than the browser's clock — consistent with `lib/localDateTime`'s rule that "today" is never read any other way.

### Two identically-labelled clear buttons would be silently ambiguous

Each `DateInput` defaults its clear button to "Clear date"; with both `start` and `end` populated, two buttons sharing that exact accessible name would leave a keyboard or screen-reader user unable to tell which one clears which field. `DateRangeField` gives each side its own (`"Clear start date"` / `"Clear end date"`).

### "Mobile sheet behavior", honestly scoped

The ticket's reference pattern implies a bottom-sheet presentation on small viewports. No modal/overlay primitive exists yet — `Drawer` is LOS-0414, three tickets and a dependency chain away, and is not listed as a dependency of this one. What ships here is real responsive behavior within that constraint: the two fields stack full-width below 480px instead of being squeezed into an unreadable side-by-side pair, documented in `date-range-field.css` as the honest interpretation of "mobile sheet" available without a sheet component to host it in.

## Known limitations or follow-ups

- No true bottom-sheet presentation on small viewports — see above. Worth revisiting once `Drawer` (LOS-0414) exists, as a possible `sheet` display variant.
- `presets` render as a plain button row with no active/selected indication once a preset's exact range is currently applied; adding that would require re-deriving whether the current value matches a preset on every render, judged unnecessary complexity for this ticket.
- Keyboard behavior is entirely native (two `<input type="date">`s and plain `<button>`s); nothing beyond what the platform already provides was needed or added.
