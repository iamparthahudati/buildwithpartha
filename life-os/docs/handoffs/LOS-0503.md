## Completed behavior

Added `POST /auth/signup` on top of LOS-0502's password service and LOS-1402's mail outbox: the codebase's first controller (`auth.api`), first unauthenticated route, and first ticket to write into the `users`/`credentials`/`terms_acceptances`/`email_verification_tokens` tables LOS-0501 migrated.

- `auth.domain` (no Spring/JPA dependency): `User` — the `public.users` aggregate. `29-PRODUCT-VOCABULARY.md` keeps the backend identity type named `User` even though the product calls it "Account"; `User.signup(...)` seeds `timeZone`/`locale`/`weekStart` with documented safe defaults (`UTC`, `en-IN`, Monday) since `25-ONBOARDING-SPECIFICATION.md` confirms those during onboarding (LOS-0513), not at signup. `Credential`, `TermsAcceptance`, `EmailVerificationToken` mirror their own tables the same way `OutboxMessage` (LOS-1402) mirrors `outbox_messages` — immutable records with a static factory, translated to/from a package-private JPA entity by the matching `auth.infrastructure` repository adapter. `RawToken`/`SecureTokenGenerator` are the email-verification-token equivalent of `RawPassword`/`PasswordHasher`: a redacted-`toString()` raw+hash pair, generated by a fast SHA-256 digest rather than Argon2id, because a generated token is already maximum-entropy and a deliberately slow hash would only cost CPU. `SignupRateLimiter` is a narrow, explicitly-not-general port (see Known limitations).
- `TermsAcceptance` writes two rows per signup (`terms:2026-08-01`, `privacy:2026-08-01` — prefix, not a schema change) because `31-PRIVACY-DATA-LIFECYCLE.md` forbids bundling terms acceptance and privacy notice acknowledgment into one consent record; the table's single opaque `terms_version` column already supported this without a migration.
- `auth.application.SignupService` is one `@Transactional` method: rate limit the caller address, validate the password policy (`PasswordService.validate`, LOS-0502), check for an existing account by normalized email, and — only for a genuinely new email — create the `User`/`Credential`/two `TermsAcceptance` rows/`EmailVerificationToken` and enqueue `MailMessageKind.EMAIL_VERIFICATION` through `common.mail.TransactionalMailPort` (LOS-1402), all in the same transaction so mail is only ever queued alongside a committed account. An email that already has an account is **not** an error: the method returns normally either way, and `AuthController` always renders the same generic `202 { "status": "PENDING_VERIFICATION" }`, so a duplicate and a fresh signup are indistinguishable from the response (`24-CRITICAL-USER-JOURNEYS.md`: "Duplicate/unknown account responses avoid enumeration"). No second account, credential, terms row or mail is created for a duplicate.
- `common.error` gained two exception types the API-wide `ApiExceptionHandler` (LOS-0213) now maps explicitly, ahead of the generic `CodedException` handler: `FieldValidationException` (safe per-field codes — e.g. `password`/`TOO_SHORT` — for policy checks that can't be a Bean Validation annotation because they need a live port such as the common-password wordlist) and `RateLimitedException` (→ HTTP 429, new `StandardErrorCodes.RATE_LIMITED`). `OpenApiConfiguration` gained a matching shared `TooManyRequests` response component alongside the existing `BadRequest`/`Unauthorized`/etc.
- `ApiSecurityConfiguration` now `permitAll()`s `POST /auth/signup` and disables Spring Security's default session-bound CSRF filter. That default (`HttpSessionCsrfTokenRepository`) was always incompatible with this app's cookie-session design and had simply never been exercised before this ticket's first real POST endpoint; LOS-0505 owns building the real cookie-bound CSRF scheme `06-SECURITY.md` and the OpenAPI `X-CSRF-TOKEN` scheme already describe. Signup itself is pre-session by definition, so it needs no CSRF token regardless of scheme.
- "Audit" for this ticket is a structured log line (`tech.buildwithpartha.lifeos.auth.audit`, `event=signup_succeeded`/`event=signup_duplicate`) following `31-PRIVACY-DATA-LIFECYCLE.md`'s allowed-fields list — never the raw email or password. This ticket does not depend on and does not build LOS-1404's real structured audit-event service; the log line is a documented placeholder LOS-1404 is expected to replace.
- "Rate limit" for this ticket is `InMemorySignupRateLimiter`: a fixed-window (5 attempts/15 minutes), single-instance, in-memory `ConcurrentHashMap` keyed by the request's client address (`06-SECURITY.md`: "Rate limit ... signup ..."). This ticket does not depend on and does not build LOS-1401's general per-IP/account/endpoint policy framework; this adapter is a documented placeholder LOS-1401 is expected to supersede outright, not extend.

## Known limitations or follow-ups

- `InMemorySignupRateLimiter` and the `auth.audit` SLF4J logger are deliberately narrow, single-ticket placeholders, not LOS-1401/LOS-1404's real infrastructure — see "Completed behavior" above. `InMemorySignupRateLimiter` also never actively evicts a key once its window has passed (only overwrites it on next use), so long-lived process memory grows with the number of distinct caller addresses ever seen; not a practical concern at this product's expected volume, and LOS-1401 is expected to replace the adapter outright rather than have it grow a cleanup job of its own.
- The rate limiter and the `terms_acceptances.ip_source` column both key/record by `HttpServletRequest.getRemoteAddr()` — the raw socket peer, not a proxy-aware resolution of the real client behind Caddy/Cloudflare. `LOS-1401`'s "proxy-aware trusted IP handling" is explicitly that ticket's job; behind a reverse proxy in production, both will currently see the proxy's address rather than the visitor's until LOS-1401 lands.
- `EmailVerificationToken.TTL` (24 hours) is a signup-time engineering default, not a legally reviewed value — reasonable and documented, but revisit if product/legal guidance narrows it.
- No account-level lockout or CAPTCHA exists; `06-SECURITY.md`'s broader "Verification before launch" gate (OWASP ZAP baseline, manual auth/IDOR/CSRF checks) is out of this ticket's scope and belongs to the identity threat-model ticket (LOS-0520).
- Terms/privacy version strings are accepted as opaque client-supplied values and simply recorded, not checked against a "current published version" registry — no such registry exists yet (real legal copy/versions are LOS-1614's job, well after this phase). If a stale client submits an old version string, this ticket does not detect or reject that; revisit once LOS-1614 defines real versioned documents.
- `auth.domain.User`'s `timeZone`/`locale`/`weekStart` fields are the first content of what `29-PRODUCT-VOCABULARY.md` calls "Profile" (owned by the still-empty `user` domain package). LOS-0513 (onboarding persistence) will need to decide how a different domain package updates fields on the same `users` row without violating `PackageBoundaryRules.domainIsolation()` — most likely a `common.identity`-style port mirroring `common.mail`'s precedent. Not this ticket's problem to solve, but worth flagging for whoever picks up LOS-0513.
- Environment note (matches LOS-0502/LOS-1402's own record of this): this environment's default `java`/Gradle daemon JVM is JDK 17 even though the project's toolchain targets 21; `JAVA_HOME` must point at a JDK 21 install (`/Library/Java/JavaVirtualMachines/temurin-21.jdk` here) for `spotlessApply`/`spotlessCheck`/`./gradlew check` to run cleanly.
