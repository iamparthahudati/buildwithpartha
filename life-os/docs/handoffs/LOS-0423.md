## Completed behavior

Adds `Table` and seven companion primitives (`TableHead`, `TableBody`, `TableRow`, `TableHeaderCell`, `TableCell`, `TableSelectAllCell`, `TableSelectCell`) to `components/navigation/`.

### Real table markup, deliberately never `role="grid"`

Every primitive wraps its real HTML counterpart (`<table>`, `<thead>`, `<tbody>`, `<tr>`, `<th scope>`, `<td>`) rather than a `div`-based reimplementation. `role="grid"` was considered and rejected: a grid is the ARIA APG's contract for a spreadsheet-like *editable* surface with its own required roving-tabindex arrow-key navigation system — nothing this ticket describes needs that. A plain table already gives keyboard users the only navigation model they actually need here: Tab moves between the real interactive controls a row contains (a selection `Checkbox`, a caller's own action button inside a `TableCell`) in normal reading order, and a screen reader's own table-navigation commands read the `scope="col"`/`scope="row"` and `aria-sort` this markup already provides, for free. Building a grid's arrow-key system on top would have been strictly more code for strictly worse accessibility than the platform already gives a real `<table>` — this reasoning is recorded directly in the component's own docstring so it is not silently rediscovered or second-guessed later.

### Selection reuses `Checkbox` without adding to its public API

`TableSelectAllCell` and `TableSelectCell` compose `Checkbox` (LOS-0311), including its existing `indeterminate` prop for the "some rows selected" state. `Checkbox` always renders its `label` visibly by design everywhere else it is used — correct for a form, wrong for a dense table row, where a full text label beside a tiny checkbox would double the row's visual weight. Rather than adding a `labelHidden` prop to the atom for one composed component's need, a scoped CSS rule (`.lifeos-table__select-cell .lifeos-choice__label`) applies the exact same visually-hidden clip technique `VisuallyHidden`/`visually-hidden.css` already use, directly to `Checkbox`'s own rendered label inside a select cell only. The accessible name still exists — `TableSelectCell.label` is a required prop, not optional, so a row's checkbox always names the specific record it selects ("Select Website refresh," never a bare "Select").

### A real bug the unit tests could not see

`TableCell`'s `truncate` prop originally set only `overflow: hidden; text-overflow: ellipsis; white-space: nowrap`, and every Vitest test (which only checks the className is present, since jsdom has no layout engine) passed cleanly. A live-browser check told a different story: the Description column in the catalog demo never actually clipped, no matter how long the text. The cause is `table-layout: auto` (this table's default) — an unconstrained `<td>` simply grows the whole column to fit its widest content, so `overflow: hidden` never has anything to hide. This is exactly the class of bug this session's `<when_to_verify>` browser check exists to catch: correct-looking CSS that is a semantic no-op against the real layout algorithm, invisible to any check that only asserts a class name.

The fix is the standard technique for truncating a cell inside an auto-layout table without opting the *whole* table into `table-layout: fixed`: `max-width: 0` paired with `width: 100%`. The browser still distributes the table's real available width across every column based on their content, but the constrained cell no longer gets to claim more of it than its neighbors' content pushes it toward — so its own `overflow: hidden` finally has real overflow to clip. Confirmed afterward by comparing the cell's actual `scrollWidth` against its `clientWidth` in the live browser (`scrollWidth > clientWidth` is the ground truth for "this text is genuinely being clipped," not just "the class is present").

### Density, sticky headers and the responsive escape hatch

`density` ("compact" | "comfortable") is set once on the `Table` root and cascades to every cell via a `data-density` attribute selector, rather than a prop each `TableCell`/`TableHeaderCell` would otherwise need to repeat. `TableHead`'s `sticky` prop pins the header via `position: sticky` within the table's own scroll container. "Responsive escape hatch" is read as the honest, domain-free floor every table needs regardless of what it contains: the table scrolls horizontally within its own wrapper rather than crushing every column or breaking the page's layout. A domain-aware transformation into stacked cards on mobile is explicitly `DataTable`'s job (LOS-0424, whose own ticket names "a responsive card renderer" directly) — deciding what a row becomes as a card needs to know which fields are the title, which are secondary, which to drop entirely, and these primitives deliberately carry no such domain knowledge.

## Known limitations or follow-ups

- Truncating one column while its siblings remain unconstrained can leave that column narrower than ideal, since `table-layout: auto` still lets untruncated columns claim as much width as their own content wants — visible in the catalog demo, where the Description column ends up quite narrow next to the longer, untruncated Name column. A screen needing more balanced column widths would set explicit widths on `TableHeaderCell` (already possible via the passthrough native `<th>` props, e.g. `style={{ width: "..." }}`) or `DataTable` (LOS-0424) may want its own column-width contract; this ticket's primitives do not invent one.
- No built-in sortable-header click handling. `TableHeaderCell.sortDirection` only sets `aria-sort`; a caller wanting a clickable sort trigger composes one inside the cell (a plain button, or `SortControl`, LOS-0422) — the ticket's explicit bullet list names `aria-sort`-level semantics, not a second sort-interaction pattern beyond what `SortControl` already owns.
- No column-resize, column-reorder, or row-drag affordances — none are named in the ticket, and `DataTable` is the composed component expected to decide whether any of those belong in this design system at all.
