## Completed behavior

Adds `Breadcrumbs` and `BackLink` to `components/navigation/`, alongside `Menu`/`AccountMenu` (LOS-0415) and `Tabs` (LOS-0416).

### Breadcrumbs: a real hierarchy, current page as text, truncation that keeps the path recoverable

`<nav aria-label="Breadcrumb"><ol>` per the ARIA breadcrumb pattern — an ordered list, because a breadcrumb trail is a real hierarchy, not an arbitrary set of links. The last item is always the current page: never a link (navigating to where you already are means nothing), rendered as plain text with `aria-current="page"` so it is announced, not only styled — `Link`'s own `current` prop exists for a different case (a link that merely points at the current page from elsewhere), so this uses a plain `<span>` instead.

Truncation is collapse-then-expand, not collapse-and-lose. A new `collapseBreadcrumbs` pure function (`breadcrumbsCollapse.ts`, following `menuPosition.ts`'s and `tooltipPosition.ts`'s precedent of a pure, independently testable core) decides what stays visible once a trail is longer than `maxVisible`: the first item (the root) and the last few items (immediate context and the current page) stay, and everything between them collapses behind a single button labelled "Show N hidden breadcrumbs." Activating it re-collapses with `maxVisible` set to the trail's full length, revealing everything — a dead ellipsis with no way back to the hidden path would have thrown away real navigation history for the sake of a shorter row. Each remaining crumb's own label also truncates with an ellipsis via CSS, with a smaller `max-width` below the 768px breakpoint — "responsive" read the same literal way `Drawer` (LOS-0414) already established: automatic by breakpoint, not a size a caller picks.

### A real bug, caught only by checking a live browser

The Vitest suite for `Breadcrumbs` passed cleanly throughout — its fixtures already used distinct `href` values per item. The catalog demo did not: its placeholder items all shared `href: "#"`. Rendering the component in a real browser and expanding the collapsed demo showed duplicated entries — `Home, Website refresh, Tasks, Projects, Website refresh, Tasks` instead of the four distinct crumbs expected. The cause was keying each `<li>` by `entry.item.href` alone; with every item sharing the same href, React could not tell them apart across the collapsed-to-expanded re-render and duplicated DOM nodes instead of reconciling correctly. Two fixes: the component now keys on `` `${index}-${entry.item.href}` `` so it is defensively correct even against a caller whose data happens to repeat an href, and the catalog demo's placeholder items were given realistic, distinct hrefs, since real breadcrumb data always has them and duplicate hrefs are not a case worth demonstrating. This is exactly the class of bug the project's `<when_to_verify>` browser check exists to catch — a snapshot-style unit test with well-formed fixtures cannot see a wiring bug that only a specific, realistic (or in this case, unrealistically sloppy) data shape triggers.

### BackLink: history only when the browser proves it is safe

A new pure function, `canGoBackWithinApp(referrer, currentOrigin)` (`backLinkSafety.ts`), decides whether `history.back()` is meaningful: it is, only when `document.referrer` is same-origin, which the browser itself sets on real in-app navigation and leaves empty (or cross-origin) on a direct load, a bookmark, a shared link, or an external referrer. When it is safe, `BackLink` renders a `<button>` whose `onClick` calls `window.history.back()`; when it is not, it renders a real `Link` (LOS-0308) to a caller-supplied `fallbackHref` instead — a history call that would either do nothing (empty history) or leave the app on whatever page preceded it entirely is not "back" from the user's point of view. Both render paths look identical; only the underlying element and its behavior differ, the same "same shape, different element underneath" approach `Link`'s own `external` case already uses.

## Known limitations or follow-ups

- `BackLink`'s safety check is `document.referrer` only. A same-origin referrer is a reasonable proxy for "reached via in-app navigation" today, since no router is wired in yet (`routes/index.ts` remains LOS-0201's placeholder) to track real navigation history directly; once one lands, it may offer a more precise signal than the referrer header, which some privacy settings or extensions can suppress even for genuine same-origin navigation (in which case `BackLink` degrades to the safe fallback rather than a broken history call — the failure mode is a caller-controlled destination, not a dead button).
- `Breadcrumbs`' expand-then-full-list interaction has no matching "re-collapse" control. Once expanded, it stays expanded for that render of the component; judged acceptable since a breadcrumb trail is read once per page view, not toggled repeatedly.
- The collapse function always reserves exactly one slot for the leading (root) item; a caller wanting a different split — more than one item preserved at the start, say — would need a new option, not something `maxVisible` alone can express.
