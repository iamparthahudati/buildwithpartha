# LOS-0504 handoff

- Status: Done
- Branch: `feature/LOS-0504-email-verification-api`
- Date: 2026-08-18

## Completed behavior

Added `POST /auth/verify-email`, the endpoint that consumes the single-use `EmailVerificationToken` LOS-0503 issues and activates the account: `UNVERIFIED` → `ACTIVE`.

- `auth.domain.User` gained `verify(Instant now)`: transitions to `ACTIVE` and records `verifiedAt`, or returns the same instance unchanged if already `ACTIVE` (a defensive no-op, not the mechanism that actually enforces single-use — see below).
- `auth.domain.EmailVerificationTokenRepository` gained `findByTokenHash` and `consume(UUID tokenId, Instant consumedAt)`. `consume` is the real single-use guard: a single conditional `UPDATE ... WHERE consumed_at IS NULL`, not a read-then-write in `auth.application`. Two concurrent requests presenting the same still-valid token both read an unconsumed row, but only one `consume` call can return `true`; the loser is treated exactly like a token someone already used. This is what the acceptance contract's "does not create unintended parallel accounts/sessions" line is actually testing for, and it is verified directly — `EmailVerificationServiceTests` has a test that forces the repository's `consume` call to lose the race and asserts the account is not activated.
- `auth.domain.SecureTokenGenerator` gained `hash(String rawValue)`: a token is looked up by re-hashing the value presented in the link and matching it against the stored hash, never by decrypting a stored value. `Sha256SecureTokenGenerator.hash` is the same digest `generate()` already used internally, now exposed on the port so `auth.application` can hash a caller-presented value without needing infrastructure access.
- `auth.application.EmailVerificationService.verify` is one `@Transactional` method: hash the presented token, look it up, reject an already-consumed or expired token, atomically consume it, then load and activate the `User`. Expiry is checked *before* attempting to consume, so an expired token is left unconsumed rather than marked used — expired and already-used stay distinguishable outcomes, matching `24-CRITICAL-USER-JOURNEYS.md`'s "Expired/used verification links offer safe resend/login paths" (LOS-0511 needs both as separate screen states, per its own acceptance contract: "invalid/expired and already-used states").
- Three new `common.error` exception types, mapped by three new `ApiExceptionHandler` methods ahead of the generic `CodedException` handler: `TokenInvalidException` (no matching token → 400, `TOKEN_INVALID`), `TokenExpiredException` (400, `TOKEN_EXPIRED`), `TokenAlreadyUsedException` (409, `TOKEN_ALREADY_USED` — the first real use of the `Conflict` shared OpenAPI response component LOS-0213/0214 registered but nothing had used yet). All three are named generically around "token", not "email verification token", since LOS-0507 (forgot/reset password) is expected to reuse them for its own single-use reset token rather than redefining equivalents.
- `ApiSecurityConfiguration` permits `POST /auth/verify-email` alongside signup; no CSRF change needed (CSRF is already globally disabled pending LOS-0505's real scheme, and verification, like signup, is pre-session by definition).
- "Audit" follows `SignupService`'s established convention: `auth.audit` SLF4J logger, event type and a safe failure reason only (`invalid`/`expired`/`already_used`), never the token value or the account's email.

## Validation performed

- `./gradlew check` (Spotless, Checkstyle, ArchUnit boundary tests, full test suite, 80% JaCoCo line/branch gate): pass. 185 tests, 0 failures; line coverage 97.2% (1046/1076), branch coverage 86.2% (163/189).
- A real bug was caught by `JpaEmailVerificationTokenRepositoryTests` during development, not just in review: without `clearAutomatically = true`, the bulk `@Modifying` update left an already-loaded `EmailVerificationTokenEntity` in the persistence context reporting its pre-update, unconsumed state on a subsequent read in the same transaction — a standard JPA bulk-update pitfall that would have mattered for real if `EmailVerificationService` ever re-read the token after consuming it (it does not, today, but the fix is the correct general-purpose one regardless).
- `EmailVerificationWiringIT` (full `@SpringBootTest`) proves the real `JpaUserRepository`/`JpaEmailVerificationTokenRepository`/`Sha256SecureTokenGenerator` beans wire together and a real verify call activates a persisted account, not only that the hand-written fakes in `EmailVerificationServiceTests` behave correctly.
- `AuthControllerTests` (full context, real `MockMvc`, no `@WithMockUser`) proves the endpoint is reachable without authentication and returns the correct status/code for a fresh token, an unknown token, a token reused after a successful verification, and an expired token.

## Known limitations or follow-ups

- No resend-verification endpoint exists yet. `24-CRITICAL-USER-JOURNEYS.md` and LOS-0511's own acceptance contract ("resend cooldown") both assume one exists, but no backlog ticket currently owns it — worth flagging before LOS-0511 (frontend) is picked up, since it will need a backend endpoint this ticket does not provide.
- `TokenInvalidException`/`TokenExpiredException`/`TokenAlreadyUsedException` are named and placed in `common.error` specifically so LOS-0507 (forgot/reset password, which names nearly identical "expired/used" acceptance criteria for its own single-use token) can reuse them directly rather than defining equivalents — not yet confirmed by that ticket's own implementation, only anticipated here.
- `EmailVerificationTokenRepository.consume`'s atomicity is proven against a real H2-backed `@DataJpaTest` (two sequential calls, second returns `false`) but not against genuinely concurrent threads/connections; the SQL-level guarantee (`WHERE consumed_at IS NULL` under READ COMMITTED, the JPA default) is what actually makes concurrent calls safe, not the test.
- No account-level lockout, CAPTCHA, or rate limiting exists on this endpoint. Unlike signup, `06-SECURITY.md`'s rate-limit list does not name plain email verification (only "verification resend"), and this ticket has no resend endpoint to rate-limit; revisit if a resend endpoint is added.
