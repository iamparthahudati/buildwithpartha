## Completed behavior

Adds `DateTimeField` to `apps/web/src/components/forms/`: a `DateInput` (LOS-0318) and a `TimeInput` (LOS-0319) grouped under one real `<fieldset>`/`<legend>`, the same pattern `DateRangeField` (LOS-0404) uses for two related native controls. A moment is one concept made of a date and a time, not two unrelated fields that happen to sit together. Both values stay `YYYY-MM-DD` and `HH:mm` strings end to end, exactly like the atoms they compose — never converted through a `Date` before the point this ticket actually needs one.

### `timeZone` is required input, not a label

Every other composed date field treats the timezone as something a caller mentions in its own description text. `DateTimeField` cannot: `timeZone` is what `resolveLocalDateTime` (new, in `lib/localDateTime.ts`) needs to check whether the chosen date and time actually name a real moment in that zone. Twice a year, in a zone that observes daylight saving, they might not:

- **Spring forward** skips an hour. On 2026-03-08, clocks in `America/New_York` jump from 01:59:59 EST straight to 03:00:00 EDT, so `02:30` never happens on any clock there — a user can still type it in, but there is no instant it could mean.
- **Fall back** repeats an hour. On 2026-11-01, clocks in the same zone go from 01:59:59 EDT back to 01:00:00 EST, so `01:30` happens twice, an hour apart — the value the user sees on screen is genuinely underspecified.

The field surfaces both directly beside the inputs that produced them, rather than leaving a caller to discover a problem only once a value fails somewhere downstream. A skipped hour is an **error** (`role="alert"`, `aria-invalid` on the fieldset) because there is no valid answer to give. A repeated hour is a **warning** (`role="status"`, non-blocking) because there is an answer — the field names the convention it uses (the earlier of the two occurrences) rather than silently picking one. A caller-supplied `error` still outranks the built-in check, the same precedence `DateRangeField`'s order check already uses.

### `resolveLocalDateTime`

Added to `lib/localDateTime.ts` alongside its siblings, since turning a local date/time/zone into an instant — and reporting when that mapping is not one-to-one — is the same kind of boundary work the rest of the module already owns. There is no direct platform API for this, so the offset is read from the zone at two reference points a full day either side of the requested time, safely outside any transition (a real IANA zone shifts at most once per calendar day):

- If the two offsets agree, nothing changed nearby and the single candidate instant they produce is correct.
- If they disagree, a transition falls on this local day. Each offset's own candidate instant is checked against the requested wall time: both matching is the fold (ambiguous, resolved to the earlier instant), neither matching is the gap (nonexistent), and exactly one matching is an ordinary time that simply sits close to the transition.

The first version of this used a single fixed-point refinement starting from the naive instant itself, which passed 16 of 17 tests and silently failed to detect the fold: the naive instant's own offset is already inside one of the two regimes, so refining from it alone converges on that regime and never surfaces the other valid instant. Probing a day either side instead of the naive point directly is what fixed it — documented in the function's own comment so the mistake is not repeated.

Both real transition dates used above are stable, known 2026 US federal DST dates (second Sunday in March, first Sunday in November), used the same way `LOS-0215`'s data builders require a "valid IANA timezone, derived rather than hard-coded" fixture rather than "whatever the next transition from today happens to be" — the tests and catalog specimens stay true regardless of when they run.

## Known limitations or follow-ups

- `readOnly` on `DateInput`/`TimeInput` inherits the cross-browser unreliability already recorded in the LOS-0317 handoff; `DateTimeField` passes it through unchanged rather than working around a problem that belongs to the atoms.
- The field does not expose the resolved instant to its caller — only the local `{ date, time }` value, matching every other LifeOS date field's contract. A feature that needs the actual instant (to persist a Time Block start, say) calls `resolveLocalDateTime` itself at submission time, the same way a caller already uses `compareLocalDates` directly rather than through a field prop.
- `resolveLocalDateTime`'s two-reference-point technique assumes at most one transition per local calendar day, true for every real IANA zone in current use; it is not a general-purpose calendar library and was not built to be one.
