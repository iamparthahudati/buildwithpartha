## Completed behavior

Adds `FilterBar` to `components/navigation/`, plus a standalone pure module, `filterUrlContract.ts`.

### No domain filters of its own

`FilterBar` takes `children` — whatever filter controls the screen actually needs (a `Select`, a `DateRangeField`, a `Combobox`) — and supplies only the shell around them: the active-filter chip row, a result count, "Clear all," and the mobile collapse. This is the same "no domain columns hardcoded" principle stated directly in `DataTable`'s own ticket (LOS-0424), applied one epic tier earlier: a generic filter shell cannot know whether a screen filters by status, assignee, or a date range, and should not guess.

### The responsive collapse renders `children` twice, not behind a media-query hook

Below the small breakpoint, the inline filter controls give way to a single "Filters" button that opens the same controls inside a `Drawer` (LOS-0414). Every other "responsive" component in this design system achieves its breakpoint behavior with a single CSS rule repositioning one set of elements (`Drawer`'s own placement collapsing to full-screen, `Menu`'s touch targets growing). A `Drawer` cannot be handled that way: it is a real, separately mounted overlay, not something `@media` alone can reposition into or out of existence. So `FilterBar` renders `children` in two places — once in an inline row, once inside the `Drawer` — and lets CSS decide which is visible, rather than adding a `useMediaQuery`-style hook to decide whether to mount the `Drawer` at all. Both copies read from the exact same caller-owned controlled state (the filter values live in the caller's own component, not in `FilterBar`), so they can never disagree — confirmed live in a browser, not just asserted: setting the Status filter through the inline `Select` on a desktop-width viewport, then resizing to mobile and opening the Drawer, showed the same "Open" value already selected in the Drawer's own copy of the same `Select`.

### `filterUrlContract.ts` is the ticket's "URL serialization contract"

Two pure, symmetric functions — `serializeFilters(filters): URLSearchParams` and `parseFilters(searchParams, keys, multiValueKeys?): FilterState` — define how a generic filter-state object round-trips through a URL's query string, independent of any specific filter schema (no filter names are hardcoded, matching `FilterBar` itself). An `undefined` or empty-string value is omitted from the serialized URL entirely, so clearing a filter drops its key rather than leaving `?status=` behind; an array value serializes as one repeated key (`?label=a&label=b`), matching `URLSearchParams.getAll`'s own read shape, and the caller must name which keys are multi-valued when parsing back, since `URLSearchParams` alone cannot distinguish "never set" from "set to one value" for a key that is allowed several.

This module deliberately does not wire itself to `history.pushState`/`popstate` the way `useDeepLinkParam` (LOS-0414) does for a single value — the ticket asks for a serialization *contract*, not a second hook, and a live multi-value URL-sync hook built on top of this contract is left for whichever future ticket (most likely `DataTable`'s own query-state composition, LOS-0424) actually needs it, so as not to build unused surface area now.

## Known limitations or follow-ups

- No live URL-sync hook ships with this ticket — `filterUrlContract.ts` defines the round-trip shape only. A screen wanting filters that survive a reload needs to wire `serializeFilters`/`parseFilters` to `history.pushState`/`popstate` itself today, the way a future multi-value sibling to `useDeepLinkParam` presumably will.
- Rendering `children` twice means any filter control with genuinely uncontrolled internal state (rather than the caller-owned controlled state every field in this design system already requires) would drift between the inline and Drawer copies. This is not a new risk specific to `FilterBar` — every field atom in this codebase is controlled by design — but it is worth stating as the assumption this component's responsive strategy depends on.
- `resultCount` is a single formatted string, not a structured `{ count, noun }` pair; a caller wanting to pluralize or localize the noun does so before passing it in, matching every other "never invent copy" component in this design system.
