## Completed behavior

Adds `DataTable<T>` to `components/navigation/` — the Epic 04 composition ticket, closing out the epic's data-display pattern set built across LOS-0410, 0411, and 0420–0423.

### The composition, not a ninth primitive

`DataTable` owns no state of its own to "compose" — every feature is a fully controlled prop, exactly matching how `Tabs` (LOS-0416), `Pagination` (LOS-0421) and `FilterBar` (LOS-0420) already work standalone: `filters`, `sort`, `pagination` and `selection` are each an optional config object the caller's own component state feeds. The "compose query state" in the ticket's own wording is read as: the composition itself *is* the query state, now living in one component's props instead of five separately wired ones. Internally, `DataTable` renders `FilterBar`, `SortControl`, the `Table` primitives, `Pagination`, `EmptyState` and `ErrorState` — nothing here reimplements what any of those five already do.

### Generic over the row type — genuinely no domain columns hardcoded

`DataTableColumn<T>` (`{ key, header, render: (row: T) => ReactNode, truncate? }`) and `rows: readonly T[]` make the component generic. Nothing about a Task, a Project, or any other record's fields exists in this file — the caller supplies both the column definitions and how each cell renders. This is the direct, literal reading of the ticket's own "no domain columns hardcoded" line, and it is why `getRowId`/`getRowLabel` are functions rather than an assumed `id`/`name` field: a generic component cannot assume a shape it was never told.

### Column headers stay non-interactive for sorting — `SortControl` already owns that

A common real-table pattern is a clickable column header that changes sort on click. `DataTable` does not do this: `SortControl` (LOS-0422) is the composed component that already owns the sort-field-and-direction interaction, and giving `DataTable` its own second, competing sort trigger would be two ways to do the same thing rather than one composition reusing the other. A column header still carries the real `aria-sort` attribute whenever `sort.value.optionId` names that column, so the semantics stay correct even though the interaction itself lives in `SortControl`'s trigger, not the header cell.

### The responsive card view, and why it avoids `:has()`

`renderCard`, when given, replaces the table entirely below the 768px breakpoint with a caller-rendered card per row — the domain-aware escape hatch `Table`'s own ticket (LOS-0423) explicitly deferred to this one. A first draft used a `:has()` selector to hide the table view whenever a non-empty card view followed it in the DOM. That was wrong for this project specifically: `:has()` reached broad browser support only in late 2023 (Firefox 121), after this project's own frozen minimum target (Firefox 114, recorded in the LOS-0406 handoff for the same reason `Intl.DurationFormat` was avoided there). The fix computes a `data-has-card-view` attribute in JS from whether `renderCard` was actually given, and scopes the mobile CSS rule off that attribute instead — no browser-support assumption beyond what the rest of this project already commits to.

### Bulk actions and selection

`selection.bulkActions` renders inside a toolbar that appears only once `selectedIds.size > 0`, alongside a caller-independent "Clear selection" control this component always supplies. Select-all reflects both a fully-checked and a partial (indeterminate) state across the currently rendered page of rows — the conventional "select all on this page" semantics, not all rows across every page, since `DataTable` has no way to know about rows on pages it is not currently rendering.

## Known limitations or follow-ups

- Selection is page-scoped by design (select-all only ever touches the currently rendered `rows`). A screen wanting a genuine "select all N matching results across every page" affordance would need to build that as an explicit additional action, not something `DataTable` infers on its own from a page's worth of ids.
- No column-resize, column-reorder, or column-visibility toggle. None are named in the ticket; a future screen needing them would need a new capability on top of `DataTableColumn`, not something this ticket adds speculatively.
- The card view has no built-in selection UI of its own — a caller wanting selectable cards would need to compose the checkbox into their own `renderCard` output, since `DataTable` cannot inject a control into an opaque, caller-rendered card the way it can into a `TableSelectCell` it renders itself.
