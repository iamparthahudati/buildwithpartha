## Completed behavior

Adds `EmptyState` to `apps/web/src/components/feedback/` (STRUCTURE.md's category explicitly lists "empty/error"). Built on `Surface` (LOS-0329, muted/unbordered) with `Heading`/`Text`/`Icon` for its content.

### `variant` picks an icon, never copy

`title` and `description` are always plain strings the caller supplies — `variant` selects a sensible default icon and nothing else. This is a direct reading of the tone guide's own component copy contract ("Components must accept semantic content... and must not invent inconsistent feature copy internally") and matches its module-examples table: Projects, Time Blocks, Notes and every other first-use empty state get their own wording, not one shared sentence a component would have to invent.

### Five variants from the ticket, not a one-to-one copy of the tone guide's table

The ticket names `first-use`, `filtered`, `search`, `permission` and `archived`. The tone guide's own empty-state table has seven rows, three of which match directly (first-use, filtered, search); `permission` matches its separate "Permission/unavailable" row (`This item isn't available.` / `Back to tasks`, chosen specifically to "state unavailability without leaking existence" — never distinguishing "doesn't exist" from "you can't see it"); `archived` has no dedicated row, so its catalog specimen follows the voice the guide's own Archive example and module-examples table already establish rather than inventing a new tone. The guide's remaining two rows — "Naturally complete" and "Missing history" — are not named variants here; nothing about `EmptyState`'s pure-layout design prevents a caller from using it for either with their own copy, so nothing was lost, only left unlabelled as its own `variant` value.

### The title only joins the page outline when a level is given

`titleLevel?: HeadingLevel` is optional; supplying it renders `title` as a real `<Heading>` at that level, joining the surrounding page's outline — right for a full-page or full-section empty state. Leaving it out renders plain emphasized text instead. A "No results" inside a Combobox's listbox or a filtered list is not a landmark in the page's document outline, and forcing every `EmptyState` into one regardless of context would be a false structural claim the same way an unnamed `Surface` section (LOS-0329) would be.

### The icon slot is icon-only, honestly

The prop is documented as accepting a `LucideIcon | false` — `false` renders none at all — rather than being called a generic "illustration" slot. There is no illustration system in LifeOS yet; `Logo` (LOS-0328) made the identical honest scoping call with a geometric placeholder rather than real artwork, and this ticket follows the same practice instead of promising a capability that does not exist.

## Known limitations or follow-ups

- No illustration artwork, by design — see above. The icon slot is ready to accept a real illustration component later without a prop-shape change, since it already takes an arbitrary override.
- `primaryAction`/`secondaryAction` are `ReactNode` slots, the same trust-the-caller shape `Alert`'s `action` slot already uses (LOS-0408); nothing structurally stops a caller from putting more than one button inside either slot beyond the naming and documentation saying not to.
- No dedicated "Optional feature off" or "Missing history" variant, matching the ticket's own five-variant scope; a caller can still use `EmptyState` for either today with its own copy, just without a named `variant` value for it.
