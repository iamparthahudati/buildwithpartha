## Completed behavior

Added `SignupScreen`, composing the already-built form primitives named in the ticket into the actual signup screen — the first real product screen in the codebase, on top of LOS-0508's `apiClient`/`authApi` and LOS-0503's `POST /auth/signup`.

- Composes `FormFieldGroup`/`FormErrorSummary`/`FormField` (LOS-0401), `TextInput`/`PasswordInput` (LOS-0314/0315), `Checkbox` (LOS-0311), `Button` (LOS-0306) and `Alert` (LOS-0408) directly — no new form primitive was written. `PasswordInput` gets `autoComplete="new-password"` explicitly (its own default is `current-password`); `TextInput` for email gets `type="email"` and `autoComplete="email"`; the name field gets `autoComplete="name"` — the password-manager/mobile-keyboard behavior the ticket names.
- The terms/privacy checkbox is one of the "very few checkboxes" `FormField`'s own docstring says "required" legitimately means "must be checked": composed through `FormField` exactly like every other field, so its `required` render prop reaches the `Checkbox`'s native `required` attribute the normal way. A separate, non-interactive `Text` line above it carries the actual `Terms of Service`/`Privacy Policy` `Link`s (`/life-os/terms`, `/life-os/privacy`, built from `VITE_APP_BASE_PATH` the same way `lib/returnPath.ts` does) — `Checkbox.label` is typed as a plain `string`, so a real link cannot live inside the box's own accessible name, and this is the established, fully keyboard-reachable way around that.
- `features/auth/model/passwordPolicy.ts` mirrors `auth.domain.PasswordPolicy`'s two constants (`MIN_LENGTH=12`, `MAX_LENGTH=128`) client-side only for the obvious pre-submit cases; whether a password is commonly exposed cannot be checked here and always waits for the server's `COMMONLY_EXPOSED` response. `features/auth/model/signupValidation.ts` mirrors `SignupRequest.java`'s Bean Validation shape (`NotBlank`/`Email`/`Size`) plus the password-length policy, reusing the exact same copy a server-reported failure would show via `signupFieldErrors.ts`'s `resolveSignupFieldError` — a blank field looks identical to the user whether caught client-side or round-tripped to the server. `legalVersions.ts` pins `TERMS_VERSION`/`PRIVACY_VERSION` to `"2026-08-01"`, the literal `AuthControllerTests.java` already exercises, so signup stays consistent with what the backend accepts today (real legal versioning is LOS-1614's job).
- **Enumeration safety**: a successful submit always renders the identical `SignupPending` view ("Check your email", "We've sent verification instructions to {email}.") regardless of whether the email already had an account — `SignupResponse` carries no field that could say otherwise, and the component has no second branch to invent one, matching `24-CRITICAL-USER-JOURNEYS.md`'s requirement directly (proven by a test that runs the identical flow twice and asserts the identical pending screen).
- **Inline + summary errors, focused correctly**: client validation failures and server `VALIDATION_FAILED` field failures both flow through one `applyFailure` function into the same `FormErrorSummary`. Getting focus right there was the real problem this ticket solved, not a detail: `FormErrorSummary` only mounts a real DOM node once `FormFieldGroup`'s registry context has a first error in it, and `FormField` registers itself from its own effect — one render cycle *after* this component's own `setErrors` commits. A plain ref read immediately after `setErrors` (and even `flushSync`, which was tried and does not cascade through that second, effect-triggered render) still reads `null`. The fix is a callback ref plus a "pending focus" flag: whenever React actually attaches the summary's DOM node — however many render cycles that took — a pending request is honored right then, and if the node is already mounted (a second failed attempt) it focuses immediately instead of waiting. The page-level `Alert` (rate limit, generic failure) has no such race — it renders directly from this component's own state — so a plain `useEffect` keyed to that state is enough there.
- Rate-limit (`429`/`RATE_LIMITED`) and any other unexpected failure render as a non-field `Alert` ("Too many attempts. Wait a few minutes before trying again." / "We couldn't create your account. Your details are still here.") without discarding any entered value, matching the tone guide's "Recoverable error" pattern.

## Known limitations or follow-ups

- **No route exists yet that actually mounts `SignupScreen` at `/life-os/signup`.** No router is wired into LifeOS (LOS-0207/LOS-0508 both record the same state), and `routes/index.ts` is still LOS-0201's empty placeholder. This mirrors how `LOS-0614` ("Compose Today screen with mock states") builds and tests a screen before `LOS-0615` integrates it — `SignupScreen` is complete and fully tested in isolation, ready for whichever ticket introduces real routing (most likely alongside `LOS-0603`'s application shell, or an earlier dedicated routing ticket if one is added to the backlog) to mount it at its canonical public route.
- Client-side password validation checks length only (`TOO_SHORT`/`TOO_LONG`); `COMMONLY_EXPOSED` can only ever come back from the server, so a common password is never caught before the round trip. This is inherent to the policy (the wordlist is backend-only) and is called out explicitly in `passwordPolicy.ts`'s own docstring.
- The email-shape check (`EMAIL_SHAPE_PATTERN`) is a deliberately simple `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`, not a copy of Hibernate Validator's own `@Email` regex — good enough to catch "clearly not an email" before a round trip, with the server's `@Email` annotation remaining the sole authority for anything more precise.
- Terms/privacy version literals (`"2026-08-01"`) are hardcoded to match the backend's current test fixtures; no "current published version" registry exists on either side yet (LOS-1614).
