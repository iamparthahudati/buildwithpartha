## Completed behavior

Adds `Timeline` to `components/navigation/` — a vertical sequence of dated milestones, each in one of four states (`completed`/`current`/`future`/`overdue`).

### `status` is entirely the caller's

Consistent with every other stateful pattern in this epic (`ConfirmDialog`'s `pending`, `TimerRing`'s `status`), `Timeline` computes nothing about whether an entry is overdue. Whether a `future`-dated milestone has quietly become `overdue` depends on "now" and a timezone — exactly the pair `lib/localDateTime.ts` exists to handle correctly — so only the caller, already holding both, can resolve it. `Timeline` just renders whatever status it is given.

### `DividerList` (LOS-0330) was considered and rejected, not silently skipped

`DividerList`'s own separator is a horizontal hairline *between* rows. A timeline's separator is the opposite: a vertical connecting line running *through* each row's own marker column, down to the next one. The two visual languages fight rather than combine — forcing `DividerList` in would mean overriding its own separator CSS away just to add a different one, so this uses a plain `<ol>` (order is genuinely meaningful here, unlike most lists in this codebase) with its own marker/line CSS instead. Read as satisfying the ticket's dependency in spirit (a real, correctly-counted list) rather than by literal composition.

### Titles stay plain text by default — `EmptyState`'s own `titleLevel` convention

A `Timeline` might render two milestones inside a Today widget or a dozen inside a dedicated project tab. Defaulting every entry's title to a real `<h3>` would be a false claim about the page's document outline in the first case. `titleLevel` is optional and undefined by default (plain, bold text); given, each title becomes a real heading at that level — the identical opt-in `EmptyState` (LOS-0410) already established.

### A real CSS bug the live-browser pass caught: the connecting line had zero height

The first version positioned the line as `.marker::after` with `height: calc(100% - var(--lifeos-space-6))`. That `100%` resolves against the *marker's own* height (its closest positioned ancestor with an explicit size) — 24px minus 24px is 0, so the line was invisible despite looking correct in the source. `getComputedStyle` confirmed `height: 0px` before the fix. The fix moves the line to `.entry::before` and sets `top`/`bottom` instead of `height`: an absolutely positioned element with both offsets set has its height solved by the box model from the entry's own real rendered size, correctly handling the entry's genuinely auto/content-derived height (a description can wrap to any number of lines) in a way a percentage `height` cannot. Confirmed after the fix via the same `getComputedStyle` check (a real, non-zero pixel height) and visually in both desktop and a 375px mobile screenshot.

### Reduced motion and print

The `current` entry's marker pulses gently via `box-shadow`, disabled under `prefers-reduced-motion: reduce` — the same pattern `TimerRing` (LOS-0427) already established for its own running-state pulse. `print-color-adjust: exact` on the marker and its connecting line keeps the status colors from being stripped when printed.

## Known limitations or follow-ups

- No built-in "load more"/pagination for a very long milestone list — a screen with many entries would need to page or filter them itself before handing `entries` to this component, the same "caller supplies the data it already has" split `DataTable`'s own filters/pagination make explicit as separate config objects.
- No click/expand interaction on an entry. The ticket names semantics and mobile layout, not an interaction model; a screen wanting a milestone to open a detail view would wrap `entry.title` in its own `Link`/`Button`, the same escape hatch `DataTable`'s `renderCard` uses.
