## Completed behavior

Adds `CommandPalette` and `useCommandPaletteShortcut` to `components/feedback/` — a keyboard-opened, `Dialog`-hosted search-and-act surface, and the standalone hook that opens one from anywhere on the page.

### Grouped listbox on `aria-activedescendant`, not real focus per option

Same real-focus-stays-on-the-input pattern `Combobox` (LOS-0403) already uses: a single `<input role="combobox">` keeps DOM focus at all times, and `aria-activedescendant` names whichever result the keyboard is currently on. Results render as a flat, grouped `role="listbox"` — each group a `role="presentation"` `<li>` wrapping its own heading and a `role="presentation"` nested `<ul>` of `role="option"` rows, which keeps every option a direct accessibility-tree child of the outer listbox despite the visual grouping. Arrow Up/Down, Home and End all navigate one flattened sequence spanning group boundaries, skipping disabled items entirely (`Menu`'s stricter precedent, not `Combobox`'s, since these are actionable commands rather than selectable data).

### `useSearchField` (LOS-0402) supplies the typing timing, not the widget

`query`/`onQueryChange` is the raw typed text on every keystroke; `onSearch` fires only after `useSearchField`'s debounce, or immediately if Enter is pressed while nothing is highlighted (the same "submit now" override `SearchField` already gives a caller). Enter's two responsibilities are resolved by priority: an active result takes it first (activate and close); only once nothing is highlighted does Enter fall through to that immediate-search override.

### "No unauthorized cached result" — read as two separate guarantees, not one

The ticket's own wording is interpreted as two things this component must never do, both caught and fixed only by driving it in a real browser (jsdom has no layout and `user.type`/`user.keyboard` can target an element directly regardless of what actually has DOM focus, so neither of these would have failed in a headless test run):

1. **Never point at content that no longer exists.** The one piece of UI state this component keeps — which result is highlighted — is stored as the item's own `id`, not its position, and derived (`effectiveActiveId`) rather than written back by an effect: if the caller replaces `groups` with a set that no longer contains that id (a fresh, differently-scoped result set arriving mid-session), nothing is highlighted, rather than a different, unrelated item silently inheriting the same numeric index.
2. **Never let one session's highlight survive into the next.** `activate()` and every `Dialog` close path (Escape, backdrop, the header's own close button) now run through one `handleClose` that resets the highlighted id before calling the caller's `onClose`. This was missing in the first pass: a real browser session — Ctrl+K open, arrow to a result, Enter to select, Ctrl+K open again — showed the *previous* result still highlighted, because closing had never cleared it. `Combobox` already clears its own `activeIndex` on every close path for the identical reason; this component just hadn't matched that precedent yet.

### The global shortcut is safe because of the modifier, not despite it

`useCommandPaletteShortcut` differs from `SearchField`'s own single, unmodified `shortcutKey` (LOS-0402): that one only fires while nothing editable has focus, because a bare letter would steal a keystroke out of any text field. Cmd/Ctrl+K cannot collide with normal typing the same way, so this fires regardless of what currently has focus — the same reserved combination other applications already use for the same purpose. `event.repeat` is checked so holding the combination down cannot reopen it repeatedly.

### A second, unrelated bug the same live-browser pass caught

The search input never actually received focus on open. `useFocusTrap`'s default (no `initialFocusRef` given) focuses "the container's first focusable descendant" — but `Dialog`'s header, which always renders before its body regardless of `titleHidden`, contains a real `<button>` (the close control) ahead of the search input in DOM order, so that button silently won every open. Fixed by giving the input a ref and passing it as `Dialog`'s `initialFocusRef`, with a regression test (`toHaveFocus()`) added specifically because the existing keyboard-interaction tests could not have caught this class of bug — `user.type(screen.getByRole("combobox"), ...)` targets the element directly and does not depend on it actually holding focus.

## Known limitations or follow-ups

- No fuzzy/ranked matching of its own — filtering `groups` for a given `query` is entirely the caller's responsibility, matching `Combobox`'s own `options` contract. A screen wanting fuzzy search would layer that into whatever it passes as `groups`, not something this component does internally.
- Item `shortcut` is display-only text (e.g. `"⌘N"`); it is never bound to a live key handler by this component. A screen wanting an item's shortcut to actually work while the palette is closed would need to wire that itself, the same way the palette's own open shortcut is wired via `useCommandPaletteShortcut`.
