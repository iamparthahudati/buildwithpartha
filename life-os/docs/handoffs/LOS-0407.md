## Completed behavior

Adds `ColorIconPicker` to `apps/web/src/components/forms/`, for the "color/icon" appearance both Project and Habit carry (`04-DOMAIN-MODEL.md`). Two real native radio groups — eight colors, twelve icons — each keyed by its own `name` attribute, under one outer `<fieldset>`/`<legend>` naming the whole field and two inner ones naming each group. Arrow-key movement, the roving tab stop and "only one selected" all come from the browser, exactly the same reason `RadioGroup` (LOS-0312) exists; none of it is reimplemented here.

### The palette is the frozen chart tokens, not a new one

LifeOS forbids a raw color literal outside `styles/tokens.css` (`verify:tokens`, LOS-0301), so this ticket could not invent eight new hex values for swatches. It reuses `CHART_SERIES_TOKENS` instead — the one existing set of eight colors already chosen in LOS-0301 to be distinguishable from each other — and gives each a human name (`colorIconPalette.ts`: `COLOR_SWATCHES`). "Named color output" means exactly that literally: the value a caller receives is `"blue"`, `"teal"`, never a hex string or a `--lifeos-*` token — the same reason a Task's status is stored as `TO_DO` rather than whatever color currently represents it, so a future repaint of the palette changes nothing about data already saved.

### "Contrast-safe preview" is proven, not assumed

`CHART_SERIES_TOKENS` were chosen in LOS-0301 to be distinguishable from each other, not proven safe as a solid fill under a white icon — nothing in the frozen `CONTRAST_REQUIREMENTS` list covers that pairing, unlike the status colors, which already do. `colorIconPalette.test.ts` computes the real ratio for every swatch with the same `contrastRatio` math `styles/tokens.test.ts` already uses, and all eight clear AA (4.5:1) against white with real margin — the lowest, amber, is 5.43:1. Because that is proven rather than assumed, the preview renders the actual chosen color as a solid fill with the actual chosen icon in white on top, rather than a smaller or lower-contrast stand-in.

### The icon list is small and curated, not the whole library

Twelve names from the approved lucide-react set (ADR-013), chosen for Project/Habit-style appearance rather than an exhaustive catalog — `11-PRODUCT-SPECIFICATION.md` §47 requires one coherent icon set with accessible labels and forbids mixing emoji into it, which is why the list stays inside the same set every other LifeOS icon already comes from rather than reaching for anything else.

### A hidden native input, not a restyled one

`Radio.tsx` keeps its native radio visible and restyles it in place with `appearance: none`, because a checkmark dot is a shape that technique can produce. A colored circle or an icon glyph is not, so here the native input is visually hidden (opacity 0, kept at full size and in the tab order) and paired with a sibling `<span>` swatch that reacts to the input's `:checked`/`:focus-visible` state through a plain sibling selector (`input:checked ~ .dot`) — not `:has()`, which is not yet safe against this project's frozen Firefox 114 minimum. The accessible name for each swatch comes from a `VisuallyHidden` span inside the same `<label>`, the same "hidden text carries the name, the input carries nothing painted" pattern `IconButton` already uses.

## Known limitations or follow-ups

- Scoped exactly to the ticket's name — a combined color **and** icon picker for Project/Habit. Label's simpler need (`29-PRODUCT-VOCABULARY.md`: "may have an optional accessible color", no icon) is not addressed here; reusing just the color-swatch markup as a standalone control is a reasonable future ticket rather than something this one should have generalized toward speculatively.
- The `forced-color-adjust: none` on the color dot is a deliberate, narrow exception to letting forced-colors mode override decorative color — documented inline, because the color is the content this control exists to choose, and a picker whose swatches all render identically would not be operable. The checked ring still switches to `Highlight`, so the selection stays visible even where the fill does not.
- No keyboard shortcut or type-ahead beyond what native radio groups already provide (first-letter jump is not a browser-native radio behavior); not required by the ticket and not added speculatively.
