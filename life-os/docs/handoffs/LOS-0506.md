## Completed behavior

Added `POST /auth/logout` (current session) and `POST /auth/logout-all` ("sign out all devices", `06-SECURITY.md`).

- Both endpoints are `permitAll()`, not gated by `.anyRequest().authenticated()` — deliberately, so they stay safely callable with **no session at all** (already logged out, expired cookie, or no cookie ever sent), satisfying the ticket's "clear cookie idempotently" requirement literally: every call returns `200 { "status": "LOGGED_OUT" }` and a cookie-clearing `Set-Cookie` header, whether or not there was anything to revoke.
- `auth.application.LogoutService` resolves the session from the raw cookie value itself (never `@AuthenticationPrincipal`, since these routes sit outside the authenticated bucket): no session found, an unknown token, or an already-inactive one is a no-op success. Only when an **active** session is actually found does a CSRF check apply at all — matching the ticket's own "require CSRF as applicable" wording exactly, rather than unconditionally. A missing or mismatched `X-CSRF-TOKEN` header throws before anything is revoked, and `AuthController` never reaches its cookie-clearing line on that path, so a rejected request leaves every cookie and server-side session state exactly as it was.
- `SessionRepository.revoke` mirrors `EmailVerificationTokenRepository.consume`'s exact shape: a single conditional `UPDATE ... WHERE revoked_at IS NULL`, proven with a real-H2 test that a second `revoke` call for the same session returns `false`. `revokeAllForUser` is the bulk equivalent for logout-all, scoped correctly with a test proving a second user's sessions are untouched.
- New `common.error.CsrfTokenInvalidException` (code `CSRF_TOKEN_INVALID` → 403) is deliberately distinct from the existing generic `AccessDeniedException`/`ACCESS_DENIED` path — folding a CSRF failure into "access denied" would hide which of the two actually failed from the caller.
- This is the first ticket to actually build CSRF *enforcement* (LOS-0505 only built the bootstrap — issuing the token). It lives in `LogoutService`, not `SessionAuthenticationFilter`: since logout is intentionally outside the authenticated-request gate, a filter-level blanket check on unsafe HTTP methods wouldn't fire for these routes anyway, and no other endpoint yet has an authenticated mutation to protect. A later ticket that does can extract a shared helper once it exists as a second real caller, matching this project's own extraction convention.
- `AuthController`'s `sessionCookie`/new `clearedSessionCookie` share every attribute except value and `Max-Age` (0 vs `Session.TTL`) — the cookie built by logout is byte-for-byte the same shape login issues, just emptied and immediately expired, so a browser that receives it reliably drops the old one.

## Known limitations or follow-ups

- CSRF enforcement exists only for logout/logout-all. The next ticket to add an authenticated mutating endpoint (LOS-0507's reset-password flow is itself unauthenticated end-to-end, so likely LOS-0513 onboarding or later) is where a shared, filter-level enforcement mechanism becomes worth extracting — duplicating `LogoutService`'s csrf-matching logic a second time, rather than a third, is the right trigger per this project's own extraction convention.
- `SessionRepository.revoke`/`revokeAllForUser`'s atomicity is proven against sequential H2 calls in the same JVM, not genuinely concurrent connections; the SQL-level guarantee (`WHERE revoked_at IS NULL` under READ COMMITTED) is what actually makes concurrent calls safe, matching the same caveat LOS-0504's handoff recorded for token consumption.
- No audit trail beyond the `auth.audit` SLF4J line exists for "which sessions/devices were signed out" — `06-SECURITY.md`'s "show safe device/activity" is LOS-0516's job, on top of this ticket and LOS-0505's `device_hint` capture.
