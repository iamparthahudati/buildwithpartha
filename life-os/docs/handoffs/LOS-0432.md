## Completed behavior

Adds `CommentComposer` and `CommentList` to `components/navigation/` — a plain-text composer plus the list of what it's posted, covering the ticket's "Plain/Markdown-safe text, pending/edit/delete, timestamps, empty/error, keyboard submission without accidental send" contract.

### "Markdown-safe" by never attempting Markdown at all

A comment body is plain text end to end, rendered with `white-space: pre-wrap` so the author's own line breaks show without any parsing step in between. `DEPENDENCY-POLICY.md`'s "a new direct package is its own reviewable ticket" rule (already applied to `BarChart`/`LineChart`/`DonutChart` choosing hand-rolled SVG over a charting library, LOS-0429) ruled out reaching for a Markdown parser inside this one — there is nothing here that could ever render as anything other than what was typed, which is what makes it safe.

### Keyboard submission that can never be accidental

Plain Enter is left completely alone — the textarea's own native newline, never intercepted. Cmd/Ctrl+Enter is the one path that sends, using the same `event.metaKey || event.ctrlKey` check `useCommandPaletteShortcut` (LOS-0426) already established rather than guessing at a platform, and held off entirely while `event.nativeEvent.isComposing` is true — `SearchField`'s own precedent (LOS-0402) for never letting a not-yet-real IME character trigger an action.

### One composer, reused as-is for the inline editor

`CommentComposer` takes `submitLabel` and an optional `onCancel` specifically so `CommentList` can reuse the identical component for "Add a comment" and inline edit — only the label ("Add a comment" vs. "Edit comment"), the submit button's text ("Add comment" vs. "Save" — `docs/29-PRODUCT-VOCABULARY.md`'s own distinction between creating and "persisting edits without changing lifecycle status") and the presence of a Cancel button change between the two.

### Edit and delete both stay local, transient state — the same split `AttachmentList` already draws

Which comment (if any) is being edited, and what has been typed into it, live in `CommentList`'s own `useState` — purely about which control is currently open, not something a caller could usefully own. `onEdit(id, body)`/`onDelete(id)` are the caller's actual network mutation; `editPending`/`editError` and `deletePending`/`deleteError` are the identical caller-owned async state shape `ConfirmDialog`'s own `pending`/`error` already use. Both close themselves on success through the same render-time state adjustment `ConfirmDialog` uses to reset its typed-confirmation field: edit mode exits when `editPending` returns to `false` with no `editError`; the delete `ConfirmDialog` closes when its target disappears from `comments`.

### Authorization is callback presence, not a disabled button

`onEdit`/`onDelete` gate whether their controls render at all — `AttachmentList`'s (LOS-0431) identical reasoning: the backend decides who may edit or delete a given comment, and a caller that already knows the answer has no button that should exist to begin with, not one to grey out.

### Two representations of every timestamp, never one

A new `commentTimestamp.ts` gives a relative string ("2 hours ago") as the visible text and a full localized absolute string as the `aria-label` a screen reader actually announces — `docs/30-CONTENT-AND-TONE-GUIDE.md`'s own "relative time supplements an absolute value where mistakes matter" rule. Built on `Intl.RelativeTimeFormat`/`Intl.DateTimeFormat` directly rather than a new dependency.

## Known limitations or follow-ups

- No `@mention` or rich-text formatting — the ticket names "plain/Markdown-safe text" specifically, and either would be its own reviewable addition, the same `DEPENDENCY-POLICY.md` reasoning that kept a Markdown parser out of this ticket.
- No optimistic "posting…" row of its own — `pending` disables the composer while a submit is in flight, but the new comment itself only appears once the caller's `comments` array actually includes it; a screen wanting an optimistic local echo would need to insert a placeholder row into its own state before the request resolves.
- `CommentList` handles one edit and one delete at a time by construction (its own single `editingId`/`deleteTargetId`), the same single-target simplification `AttachmentList`'s one `deleteTargetId` already uses.
