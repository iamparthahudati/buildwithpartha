## Completed behavior

Added `POST /auth/forgot-password` (request a reset) and `POST /auth/reset-password` (consume the token and set a new password), completing the identity epic's password-recovery flow.

- `auth.domain.PasswordResetToken` mirrors `EmailVerificationToken` exactly, over the `password_reset_tokens` table LOS-0501 already migrated. Its `TTL` is one hour — deliberately shorter than email verification's 24 hours, matching the ticket's own "single-use short token" wording, since a reset link is both more sensitive and meant to be used within minutes.
- `ForgotPasswordService.request` is enumeration-safe the same way `SignupService`'s duplicate-email handling is: an unknown email, or one belonging to an account that isn't yet `ACTIVE`, returns normally with no token issued and no mail sent — indistinguishable from a real request at the API layer.
- `ResetPasswordService.reset` checks token validity in the same order LOS-0504 established (not-found → already-used → expired → only then attempt the atomic `consume`), and validates the new password's policy **before** consuming the token, so a policy violation doesn't burn a still-valid link. On success it rehashes the credential (reusing `Credential.rehash`, the same method LOS-0505's login rehash-on-login path added), revokes **every** session for the account via `SessionRepository.revokeAllForUser` (`24-CRITICAL-USER-JOURNEYS.md`: "Single-use reset updates the password, revokes required sessions and sends a security notice"), and enqueues a `SECURITY_ALERT` mail. No new session is issued — the caller logs in again with the new password.
- Reused `TokenInvalidException`/`TokenExpiredException`/`TokenAlreadyUsedException` without any changes — LOS-0504 named these generically for exactly this reuse, and the reuse is confirmed working end to end here.

## A real, subtle bug found and fixed (not just for this ticket)

`PasswordResetWiringIT` caught a genuine correctness bug in infrastructure two tickets already merged: **`@Modifying(clearAutomatically = true)` without `flushAutomatically = true` silently discards any other entity's pending, unflushed change in the same transaction.**

`ResetPasswordService` rehashes the credential (a plain JPA merge, which Hibernate may leave unflushed pending dirty-checking) and then immediately calls `SessionRepository.revokeAllForUser` — a bulk `@Modifying` query. `clearAutomatically = true` (added correctly by LOS-0504 to fix *its own* stale-read bug) detaches every managed entity from the persistence context the instant the bulk update runs. Because `flushAutomatically` defaults to `false`, nothing had forced the credential's pending UPDATE to disk first — it was detached, still dirty, and never written. The endpoint reported success and the audit log confirmed it, but the password silently stayed unchanged.

Fixed by adding `flushAutomatically = true` alongside `clearAutomatically = true` on **all three** existing conditional-update queries, not only the new one this ticket added — the same bug is latent in `EmailVerificationTokenJpaRepository.consumeIfUnconsumed` (LOS-0504) and `SessionJpaRepository.revokeIfActive`/`revokeAllForUser` (LOS-0505/0506); it happened not to manifest in those tickets' own flows only because of the specific order their callers already saved things in, not because the flag was unnecessary there. Added a dedicated regression test, `JpaSessionRepositoryTests.revokeAllForUserDoesNotDiscardAPendingUnflushedChangeToAnotherEntity`, that reproduces the exact mechanism (a pending `CredentialEntity` change, then a `SessionEntity` bulk update) independent of `ResetPasswordService`, so this can't silently regress again from either direction.

## Known limitations or follow-ups

- `PasswordResetRateLimiter` is IP-address-only, matching every other in-memory limiter this epic has built; `LOS-1401` is expected to supersede all of them.
- Reset-password (the token-consuming endpoint) is not itself rate limited, matching how email verification's consuming endpoint was also left unlimited — only the request-issuing side is, consistent across both flows.
- The `flushAutomatically`/`clearAutomatically` interaction this ticket found is worth a mental note for any future `@Modifying` query added to this codebase: **always pair them** when the query might run in a transaction alongside other pending writes, which in an aggregate-per-transaction style service is essentially always.
