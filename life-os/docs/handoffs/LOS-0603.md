## Completed behavior

Built the LifeOS application shell — composing `Sidebar` (LOS-0601) and `TopBar` (LOS-0602), a routed `main`, live regions, an overlay root, an error boundary, and the first real routing this app has had — per `docs/backlog/EPIC-06-SHELL-TODAY.md`, `docs/23-NAVIGATION-AND-ROUTES.md`, `docs/22-INFORMATION-ARCHITECTURE.md`, `docs/wireframes/02-SHELL-TODAY.md`, and `02-ARCHITECTURE.md`'s own "React Router owns protected routes under `/app`" line. `RequireAuth` (LOS-0508), `AppProviders` (LOS-0508), and every already-built screen (LOS-0509–LOS-0519) existed in isolation, each explicitly deferring "where this actually mounts" to this ticket; this is where they compose into a real app.

- **Dependency — `react-router-dom@7.18.2`** (`apps/web/package.json`/`package-lock.json`): the first routing library in the frontend. Already named as the locked architectural choice in `02-ARCHITECTURE.md` before this ticket; `DEPENDENCY-POLICY.md`'s "application tickets don't add direct dependencies as incidental cleanup" is about scope creep on unrelated tickets, not about the one ticket whose entire acceptance contract is "protected routing." Exact-pinned, `npm ci`-verified, `verify:dependencies` passes.

- **`components/layout/AppShell.tsx`** (+ `app-shell.css`, new `components/layout` module):
  - Renders `Sidebar` before the header row carrying `TopBar` in DOM order regardless of visual (CSS) layout, per LOS-0602's own handoff instruction.
  - **Skip link**: `Sidebar` only renders its own skip link in normal (non-`drawer`) mode; its `drawer` mode renders nothing while closed (`Drawer` returns `null`). Since `AppShell` renders exactly one `Sidebar` instance and switches its `drawer` prop by viewport, `AppShell` renders its own skip link only while `isMobile` — filling exactly the gap `Sidebar`'s own leaves — and passes `skipLinkId` through so `Sidebar`'s own (desktop) skip link points at the real `main` instead of its unrelated default. The two are never both present, so there is exactly one skip link, with one accessible name, at any viewport.
  - **Mobile navigation**: `useMediaQuery` (new hook, `useSyncExternalStore` over `window.matchMedia`, avoiding a `useState`/`useEffect` pair `eslint-plugin-react-hooks`'s `set-state-in-effect` rule now flags) decides `Sidebar`'s `drawer` mode. `AppShell` renders the one "Open navigation" trigger neither `Sidebar` nor `TopBar` has (the mobile wireframe's `[Menu]` sits outside both components' own boundaries); `TopBar`'s own "More" overflow drawer (LOS-0602) stays a separate, independent mobile trigger for a different action set (Notifications/focus/Account) — consolidating the two would mean reaching into either component's internals, which is not this ticket's job.
  - **Overlay root**: `#lifeos-overlay-root` is a reserved mount point for future portal-based overlays. `Dialog`/`Drawer`/`CommandPalette` still render in place, not through a portal — revisiting those already-shipped, already-tested components is out of scope here. `ToastViewport` (LOS-0409) is mounted here now, since nothing mounted it anywhere before this ticket; `ToastProvider`'s queue existed with no visible surface.
  - **Focus and announcement on navigation**: `23-NAVIGATION-AND-ROUTES.md`: "Route changes move focus to the page heading or a deliberate focus target and announce the new title once." `main`'s own `tabIndex={-1}` is the deliberate target (the same pattern `App.tsx`'s former placeholder used); `useAnnouncer` (LOS-0327) is the "announce ... once" half, already built and waiting for a caller. Both are skipped on the very first render — stealing focus from wherever the browser or a deep link already placed it on initial load is not what "route changes" means. `document.title` is also kept in sync, a small addition the ticket doesn't name but that "announce the new title" implies for a real SPA.
  - **Error boundary**: wraps `<Outlet/>`, keyed by `location.pathname` so a caught error does not strand every later page behind the same frozen fallback.
  - `resolveRouteTitle` (new export on `components/navigation/navigationDestinations.ts`) is the one place `TopBar`'s `contextLabel`, the live-region announcement, and `document.title` all agree — reusing `isNavDestinationActive`'s own prefix matching rather than a second, divergent notion of "current route."

- **`components/feedback/ErrorBoundary.tsx`**: a class component (React only recognizes `getDerivedStateFromError`/`componentDidCatch` on one) rendering `ErrorState`'s `scope="page"` fallback. Never logs or renders the actual error/stack — `ErrorState`'s own contract already forbids that, and a caught render error is exactly the internal detail `06-SECURITY.md` keeps out of the UI.

- **`hooks/useMediaQuery.ts`**: the one JS/CSS breakpoint bridge the shell needs, since `Sidebar` has zero built-in responsive behavior of its own (`drawer` is caller-chosen, not viewport-inferred — confirmed by `sidebar.css` having no `@media` rules at all).

- **`app/AppRouter.tsx`** — the complete canonical route table from `23-NAVIGATION-AND-ROUTES.md`, plus `/life-os/cancel-deletion` (LOS-0518 grace-period follow-up's own deferred note) and `/life-os/app/onboarding` (`docs/wireframes/01-AUTH-ONBOARDING.md`'s own path):
  - Public: landing (index), signup, login, verify-email, forgot-password, reset-password, cancel-deletion, privacy, terms, unavailable, and a public 404.
  - Protected, standalone (no shell chrome): onboarding — the wireframe's own layout is a minimal "LifeOS ... Sign out" header and step rail, not the full sidebar/top-bar shell.
  - Protected, inside `AppShell` (`RequireAuth` wraps a `ProtectedShell` that reads the session `RequireAuth` already guarantees non-null and hands `AppShell` its props/callbacks — `AppShell` itself stays purely props-driven, the same shape `Sidebar`/`TopBar` already are, never reaching into `@features/auth` or `@state` on its own): every primary `/app/*` destination from the route map, `/app` redirecting to `/app/today`, and a private 404 inside the shell.
  - Every protected route without a real screen yet (every one except Settings — later Epic-06-onward tickets' job) renders `routes/ComingSoonRoute.tsx`, a shared, honest "this screen has not been built yet" placeholder — no invented sample data, matching `App.tsx`'s own former placeholder's stance and the tone guide's fixture-data rule. `routes/NotFoundRoute.tsx` (a `variant` prop distinguishes the public/private recovery destination) and `routes/UnavailableRoute.tsx` are real, per the wireframe's own "Unavailable and Not Found use `[C] ErrorState`" line.
  - `routes/SettingsRoute.tsx` is the one non-placeholder new wiring: `:section?` URL param ↔ `SettingsScreen`'s `initialSection`/`onSectionChange`, so the active tab is a real, shareable, back-button-able route.
  - Signup/Login/VerifyEmail/ForgotPassword/ResetPassword/Onboarding/CancelDeletion route files mount their already-built screens as-is (all default to `window.location.assign` navigation internally, unchanged) — none needed new wiring beyond a route entry.

- **`app/AppProviders.tsx`**: added `ToastProvider`, composed outermost (toasts are meant to survive an account switch/logout, unlike the query cache and session `AuthSession` already clears on those events) — nothing mounted it before this ticket, since `ToastViewport` had nowhere to live until `AppShell` existed.

- **`app/App.tsx`**: replaced LOS-0201's placeholder foundation view with `AppProviders` wrapping `AppRouter`. The now-unused `.foundation*` CSS (explicitly commented "replaced by the app shell ticket" in `global.css`) is removed.

## Known limitations or follow-ups

- **No `GET /auth/session` endpoint** (flagged since LOS-0506/LOS-0508): a full page reload of a protected route always starts from `{ user: null }`, so `RequireAuth` redirects to login even with a still-valid session cookie, every time. Unchanged by this ticket — building it is its own reviewed identity ticket, not a side effect of routing.
- **Every protected primary route except Settings is `ComingSoonRoute`**, by design — Today (LOS-0608), Tasks, Projects, and the rest are later Epic-06-onward tickets. The route paths, `AppShell` wiring, and 404 behavior around them are real and tested now, so those tickets replace one `<Route>` element each rather than touching routing.
- **Public pages (landing, privacy, terms, and every existing auth screen) have no skip link of their own** — neither `LoginScreen`/`SignupScreen` nor the placeholder pages provide one, and there is no shared shell wrapping public routes the way `AppShell` wraps protected ones. `23-NAVIGATION-AND-ROUTES.md`'s skip-link line is fully met inside the app; extending it to the public surface is a reasonable follow-up, not something this ticket's "application shell" scope covers.
- **Overlay root is reserved but unused by existing overlays**: `Dialog`/`Drawer`/`CommandPalette` still render in place rather than through a portal into `#lifeos-overlay-root`. Not a regression (nothing portals anywhere today), but a later ticket revisiting those components could point them at it.
- **Quick Add's trigger** (no canonical route — it's a dialog, LOS-0604) shows an info toast ("Quick Add isn't available yet.") via the newly-wired `ToastProvider`/`ToastViewport` rather than navigating anywhere; LOS-0604 replaces that handler with the real dialog.
