# LOS-0311 to LOS-0314 handoff

- Status: Done
- Branch: `feature/LOS-0311-form-controls`
- Date: 2026-08-17

Four form controls delivered together at the owner's request. Each is recorded separately in the status ledger.

## The shared decision

All four are **native inputs with real labels**, styled rather than replaced. The alternative — a styled `div` with an ARIA role and a click handler — has to re-implement keyboard activation, form participation, the label relationship and the disabled state, and one of those always ends up subtly wrong. `appearance: none` keeps the element and its behaviour while letting the design take over its appearance.

`fieldIds.ts` derives the control, description and error ids in one place. Every control needs the same three relationships and getting them wrong is silent — a description that is not referenced is simply never announced — so the wiring is centralised rather than repeated. The error is placed **before** the description in `aria-describedby`, so it is announced ahead of a hint the user has probably already read.

## LOS-0311 — Checkbox

Indeterminate is set imperatively through the DOM property, because it cannot be expressed as an attribute; that is why the component holds its own ref internally and merges it with any forwarded one. The full row is the click target, which makes the 44px minimum easy to meet, and clicking the label text toggles the control through the native `htmlFor` relationship rather than a handler.

## LOS-0312 — RadioGroup

A real `<fieldset>` with a `<legend>` around real radio inputs sharing a `name`. Arrow-key navigation, the single roving tab stop and the "only one selected" rule are all the browser's — none of it is re-implemented, which is the entire reason to use the native grouping. Individual options carry their own descriptions; the error belongs to the group.

The legend is a visible element rather than an `aria-label`, so the group's name is readable by everyone.

## LOS-0313 — Switch

A switch is for a setting that takes effect immediately; a checkbox is for a value submitted with a form. Choosing the wrong one misleads the user about when their change actually happened, so the component documents the distinction rather than leaving it to convention.

Built on a native checkbox with `role="switch"`, keeping keyboard activation and form participation while being announced as on/off. While `saving`, a second toggle is refused — otherwise the second change would be applied on top of an unconfirmed first — and the pending state is carried by `aria-busy` plus a visually hidden label, so it is announced rather than only shown. The visually hidden input keeps the tab stop; the track renders the focus ring on its behalf.

## LOS-0314 — TextInput

The label is always a real `<label>` bound by `htmlFor`. A placeholder is never a label: it disappears the moment the user types, leaving them no way to check what the field was for. `labelHidden` hides it visually while keeping it for assistive technology.

The focus ring is drawn on the wrapper rather than the bare input, so it surrounds the affixes and the clear button too. The clear button is deliberately `tabIndex={-1}`: it duplicates something the keyboard can already do, and a tab stop between every field would slow keyboard users down. It is hidden entirely when the field is read-only or disabled, since there is nothing to clear. Success is announced politely through `role="status"` and never renders alongside an error.

Mobile keyboard hints (`inputMode`, `enterKeyHint`) and password-manager attributes (`autoComplete`, `type`) pass straight through to the native input rather than being filtered.

## Known limitations or follow-ups

- The checkbox tick and radio dot are inline SVG data URIs with a hard-coded white stroke, so they do not follow forced-colors mode the way a mask would. The surrounding fill does switch to `Highlight`, so the state remains visible, but a masked mark would be more correct — worth revisiting at LOS-0332.
- `Switch` has no built-in failure path. When a save fails, the caller must return the control to its previous state and supply an `error`; the component cannot know on its own.
- `TextInput` shows the clear button based on a controlled `value`. An uncontrolled field cannot show it, which is intentional but means clearing is a controlled-only feature.
- Field message layout assumes a left-aligned control. It will need review under right-to-left once localisation is in scope.
