## LOS-0326 — Tooltip

A tooltip is supplementary and nothing else. It is invisible on touch, gone the moment the pointer moves, unreachable by a magnifier user who has scrolled past it, and absent from a printed page. `content` is therefore typed as a plain **string**: a link or a button inside a tooltip can be seen but, for most people, never reached, and making that a type error is stronger than a convention.

Hover opens after 400ms, so a pointer crossing a toolbar does not flash five tooltips on the way. Focus opens immediately — a keyboard user has already committed to the control, and a delay there is just a pause. Escape closes it and **keeps it closed** while the pointer is still on the control; without that latch it reopens on the next pointer event and the dismissal means nothing. Escape is not stopped from propagating, because it usually also means "close the dialog I am in".

The trigger is cloned only to receive `aria-describedby`. The listeners live on the wrapper and catch the same events as they bubble, so wrapping a control in a tooltip cannot quietly replace a handler the caller already gave it. The wrapper carries one `jsx-a11y/no-static-element-interactions` suppression with the reasoning inline: it has no role, no tab stop and no behaviour of its own.

Collision handling is a pure function, `resolveTooltipPosition`, so the rules can be tested without a layout engine: flip to the other side only when that side is genuinely better, clamp horizontally to the viewport, and for a tooltip wider than the viewport pin the near edge so at least the beginning is readable.

## LOS-0327 — VisuallyHidden and live regions

Hiding text from sight without hiding it from assistive technology is easy to get almost right: `display: none` removes it from the accessibility tree, `text-indent: -9999px` leaves a scrollable region, a zero height with `overflow: hidden` drops the text in some engines. The rule clips a 1×1 box out of flow.

`LiveRegion` is **always rendered, even while empty**. A live region that appears at the same moment as its text is frequently not announced at all — assistive technology has to be watching the node beforehand — and that is the single most common reason a status message silently never arrives.

`useAnnouncer` (`hooks/useAnnouncer.ts`) is the anti-spam half. A value that updates often — a running timer, a save-on-keystroke indicator, a list refreshing behind a filter — writes to a live region every time it changes, and the user hears a stream of interruptions with no way to stop it. The first announcement publishes immediately, because the first one is usually the meaningful one; anything arriving inside the quiet window is held and only the newest survives it. A burst that keeps arriving stays throttled rather than draining one message per tick.

## LOS-0328 — Logo and wordmark

Original LifeOS marks. The reference screens are not a source of identity: the wordmark is the product name set in the LifeOS type scale, and the symbol is a plain geometric placeholder — a rounded frame around a climbing line — drawn in `currentColor` and sized in `em`, so a mark inherits the colour and size of whatever names it instead of carrying a fixed pixel box that stops matching at 200% zoom.

A lockup hides its symbol from assistive technology, because the name beside it already carries the meaning. A bare symbol takes a `label` that names the **destination** ("LifeOS home"), not the picture. A test asserts no "One System" string can appear in the rendered output.

## LOS-0329 — Surface

The card primitive: background, border, radius, elevation, padding, and no layout of its own, so a Today widget and a project row can share it without inheriting each other's grid.

Two decisions worth keeping:

- `interactive` is **styling only**. Making a whole card clickable means either a `div` with a click handler, which no keyboard reaches, or nesting links and buttons inside a button, which is invalid. The card follows the `:focus-within` of the real control inside it instead of inventing a second tab stop.
- `as="section"` only becomes a labelled region when there is a `title`. An unnamed landmark is worse than no landmark: it appears in the landmark list with nothing to tell it apart from every other one.

A raised surface keeps its border, because a shadow disappears in forced-colors mode and would leave the card with no edge at all.

## LOS-0330 — DividerList

Rows separated by a border on each row after the first, so there is no separator element between rows. A `<ul>` whose children alternate between `<li>` and a decorative `<div>` is invalid, and assistive technology reports the item count wrongly — which matters, because "how many are there" is a question a screen-reader user asks constantly.

The list is a real `<ul>` by default and `as="div"` renders a `role="group"` for rows that are not a list, such as a settings panel, where claiming a count would be a small lie. A React context passes the row element down, so a call site cannot mismatch a `<div>` row inside a `<ul>`.

## Known limitations or follow-ups

- Tooltips do not appear on touch, by design. Any information that matters must also exist in visible copy — a rule for every screen ticket, not something this component can enforce.
- Collision handling flips and clamps but does not reposition on scroll or resize while open; a tooltip closes on pointer leave and blur, so the window is short. Revisit if a sticky-hover case appears.
- `Tooltip` carries one justified `jsx-a11y` suppression on its wrapper.
- The `Logo` symbol is a placeholder. It is original and safe to ship, but a designed mark is still open work; nothing depends on its geometry.
- `Surface` does not implement the full-card link pattern (a stretched `::after` over the card). That belongs to the first composed card that needs it.
