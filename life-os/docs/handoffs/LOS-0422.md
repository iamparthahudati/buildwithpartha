## Completed behavior

Adds `SortControl` and `ViewToggle` to `components/navigation/`.

### SortControl: one trigger, a stable label, direction by reselecting the field

The trigger reads "Sort: {field}" with a leading direction arrow and a `VisuallyHidden` word ("ascending"/"descending") — direction is never carried by the arrow's shape or color alone. The field picker reuses `Menu` (LOS-0415) rather than a second dropdown pattern; every other trigger-plus-popup composition in this design system (`AccountMenu`, `PageHeader`'s overflow actions) already does the same.

Picking the field that is *already* selected toggles its direction, rather than requiring a second, separate direction control — the interaction a user reaching for "sort by the same thing, reversed" actually wants. Picking a *different* field keeps the current direction unchanged: nothing in `SortControl` can know whether "Date created" descending or "Name" ascending is the more natural default for a caller's own field, so it does not guess. Confirmed live in a browser: reselecting "Name" from the menu flipped the trigger from "Sort: Name" to "Sort: Name, descending" — the hidden direction word updating along with the visible icon.

### ViewToggle: a toggle-button group, not a radiogroup

`role="group"` wrapping three real `<button>`s, each carrying `aria-pressed` for whether it is the current view. This is a deliberate choice against `role="radiogroup"`/`radio`, which would be the more common pattern for "exactly one of several mutually exclusive options selected" — but a view preference is presentation (how the same data is arranged on screen), not a set of mutually exclusive *answers* the way a radio group's options are. `aria-pressed` states "this is currently on," which is the honest description of what switching between list, grid and table actually does. Confirmed live: clicking "Grid view" moved `aria-pressed="true"` to exactly that button and `"false"` to the other two, both in the DOM attributes and in the visible pressed styling.

The three modes are read as this design system's own closed vocabulary — "list, grid, table" is the ticket's own literal wording, not domain data the way `FilterBar`'s filter fields or `Menu`'s items are — so `ViewMode` is a fixed three-value union rather than a caller-supplied list. An optional `modes` prop narrows which of the three are *offered*; it does not add a fourth.

## Known limitations or follow-ups

- `SortControl` supports a single active sort field, not a multi-column sort. A screen needing "sort by status, then by due date" would need a different component shape.
- `ViewToggle`'s three modes are fixed at the type level. A future screen needing a fourth view (a calendar, say) needs either a new component or a deliberate extension of `ViewMode`, not a caller-supplied option — a conscious trade favoring a small, predictable vocabulary over open-ended flexibility for what the ticket frames as this design system's own chrome, not domain data.
