## Completed behavior

Adds `MetricCard` to `components/navigation/`, on `Surface` (LOS-0329) and `Metric` (LOS-0305).

### Built on `Metric`, not a heading

A first draft rendered the number with `<Heading level={3}>`. That is wrong: a raw metric value is a data point, not a document-outline entry, and putting it in the heading hierarchy would let a page's outline read "…, 42, …" between real section headings. `Metric` — already built in LOS-0305 for exactly this — gives tabular numerals for free and renders its label as real, visible, selectable text (its own docstring: "rather than a `title` or `aria-label` so it is visible, translatable and selectable like any text"), which is also a better match for the ticket's own "label" requirement than a hidden accessible name would have been.

### One discriminated `status`, not four optional props

`status: MetricCardStatus` is `{ type: "ready"; value } | { type: "loading" } | { type: "error"; message; onRetry? } | { type: "empty"; message? }` — the same shape `Combobox`'s single/multiple split and `MenuItemDescriptor`'s item/separator split already use in this codebase. It rules out impossible combinations (a value shown while also loading, an error with no message) as a type error rather than a runtime check nobody remembers to add. Because `Metric`'s own `value` prop accepts any `ReactNode`, that turned out to be the one slot that actually needs to vary across states — a `Skeleton` while loading, an `InlineMessage` on error, plain text for empty — while the label beside it stays real, visible text throughout every state, including loading, so a screen reader reading the card always has "Open tasks" available even before the number exists.

### A trend's color follows the caller's sentiment, not the arrow's direction

`MetricTrend.isPositive` is a separate field from `direction`, deliberately: a falling count is good news for "Open tasks" but a rising count of the same shape is bad news for "Overdue tasks," and the component has no way to know which is which from the number alone. The color class (`positive`/`negative`/`neutral`) is derived from `isPositive`, not from `direction === "up"` — confirmed live in a browser rather than only in a snapshot test, with a falling Open-tasks metric rendering green beside a rising Overdue-tasks metric rendering red, side by side, both in the same demo row. A `"flat"` direction is always neutral regardless of `isPositive`, since "no change" cannot be sentiment-colored either way.

"Numbers and trend have accessible text" is satisfied on two levels: the trend's direction icon (`TrendingUp`/`TrendingDown`/`Minus`) and the value's own text (e.g. "12%") are both always visible — color is never the sole signal — and a `VisuallyHidden` word ("increase"/"decrease"/"no change") backs the icon for anyone who cannot perceive its shape or the surrounding color at all.

## Known limitations or follow-ups

- No built-in loading announcement. `Skeleton` is `aria-hidden` by its own LOS-0324 design, and `MetricCard` does not add a live-region announcement for the loading→ready transition — matching `Alert`'s and `InlineMessage`'s own default-to-silent precedent (only the caller knows whether a given render is worth interrupting for), and avoiding a dashboard of several `MetricCard`s all announcing "Loading" simultaneously on page load. A screen that genuinely needs the transition announced can wrap the card in its own `LiveRegion` (LOS-0327).
- `period` is shown only alongside a `"ready"` status; a caller wanting the period text to persist visibly through the loading state (rather than disappearing and reappearing) would need a different prop shape than this ticket's four-state `status` union provides.
