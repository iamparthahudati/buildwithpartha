## Completed behavior

Adds `Tabs` to `components/navigation/`, alongside `Menu`/`AccountMenu` (LOS-0415).

### Automatic activation, sharing Menu's roving-focus mechanics

Each tab is a real `<button role="tab">` with a roving `tabIndex` — the selected tab gets `0`, every other tab gets `-1` — the same mechanics `Menu` (LOS-0415) uses for its items. `ArrowRight`/`ArrowLeft` move focus among enabled tabs and select immediately as they go (automatic activation, the ARIA APG's default recommendation for tabs), rather than requiring a separate `Enter`/`Space` to commit a highlighted-but-not-yet-selected tab. `Home`/`End` jump to the first/last enabled tab; disabled tabs are skipped by both, and by wrapping at either end. Clicking a tab needs no extra handling — a native `<button>` both selects and focuses itself on click for free.

### Panels are lazy-mounted once, then kept mounted and hidden

A panel is not rendered into the DOM at all until its tab has been selected once; after that first selection it stays mounted, toggled with the `hidden` attribute rather than being unmounted on every switch away. This is the ticket's "lazy panel loading without losing semantics" read literally both ways: content that fetches on mount (a chart, a table) does not fetch until the user actually opens that tab, and a panel already visited does not lose scroll position or local component state the next time the user switches back to it. Every activated panel stays in the DOM specifically so the currently-selected tab's `aria-controls` never points at an element that does not exist — `hidden`, not removal, is what keeps the ARIA relationship valid at every step.

This was confirmed live in a browser, not just in jsdom: the catalog's demo panels stamp their own first-mount timestamp in local state and never update it again. Switching from Overview to Activity and back showed Overview's timestamp unchanged, proving no remount happened — the kind of behavior a snapshot test alone cannot show as convincingly as watching it not change across a real interaction.

### "URL/local variants" means one controlled component, not two

`Tabs` takes a plain `selectedId`/`onSelectedIdChange` pair and has no opinion on what backs it. The catalog demonstrates both variants side by side: `TabsLocalDemo` backs it with `useState` (selection forgotten on reload), and `TabsUrlDemo` backs it with `useDeepLinkParam` (LOS-0414) so the selection survives a reload and integrates with the browser's own Back button. This is the same "component owns the mechanism, caller owns the state" split `DetailPanel`'s `open`/`onClose` already uses — inventing a second `Tabs`-like component for the URL case would have duplicated everything except which hook feeds it.

That choice surfaced a real correctness requirement: because `selectedId` is a controlled prop, it can change from *outside* `Tabs`'s own click/keyboard handlers — exactly what happens when the URL variant's selection moves because the user pressed the browser's real Back button. A first version only activated a panel from inside `select()`, so a selection arriving that way would never get its panel mounted at all. The fix adjusts `activatedIds` during render (React's own documented pattern for derived state, the same one `ConfirmDialog`, LOS-0413, and a LOS-0414 catalog demo already use) whenever `selectedId` names a tab not yet in the set — regardless of how it got there. Confirmed live: switching the URL-synced demo to "Activity" and then calling the browser's own `history.back()` correctly reverted both the URL and the selected tab.

### Counts and badges are caller content, not a `count` prop

`TabItem.badge?: ReactNode` accepts anything — the catalog demo passes a `CountBadge` (LOS-0309) — rather than `Tabs` inventing its own count-formatting logic, matching the same "structure here, copy and content from the caller" split every other composed component in this design system uses.

### Overflow on mobile is a scrolling tablist, not a "more" menu

The tab list is `overflow-x: auto`, `flex` with `flex: none` items, so more tabs than fit in the width simply scroll horizontally rather than wrapping to a second row (which the ARIA tabs pattern does not support) or requiring a separate overflow-menu component the ticket did not ask for. `pointer: coarse` restores the full 44px touch target on the tab buttons, matching every other interactive control in this design system.

## Known limitations or follow-ups

- `moveFocus`'s "next tab" calculation is derived from `selectedId`, not from which tab currently holds real DOM focus. These stay in sync on every realistic path (click, arrow key, or tabbing in via the roving `tabIndex`, which always lands on the selected tab), but a contrived case — a caller changing `selectedId` externally while a *different*, now-non-current tab still holds keyboard focus — could make the next arrow-key press jump relative to the new selection rather than the tab physically focused. Judged acceptable: fixing it would require tracking DOM focus as separate state from selection, and the scenario needs an external selection change to land while the tablist itself still holds focus, which is unusual in practice (URL changes typically originate from browser chrome, not from within an already-focused tablist).
- No overflow "more" menu — a scrolling tablist is the mechanism for more tabs than fit, per the ticket's literal "overflow on mobile" wording; a future screen needing a collapsing/grouped overflow menu would need a new pattern, not an option on this one.
- `TabItem.panel` is a plain `ReactNode` supplied upfront in the `items` array, not a render function. Constructing a lightweight React element eagerly is cheap since React does not invoke a component's function body until it is actually mounted, so this does not weaken the lazy-mount guarantee — but a caller wanting to avoid even the cost of building the element description before a tab's first visit would need a different API shape.
