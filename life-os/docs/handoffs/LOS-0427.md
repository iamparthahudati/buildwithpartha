## Completed behavior

Adds `TimerRing` to `components/feedback/` — a duration/progress/state/actions display built on `ProgressRing` (LOS-0322).

### No `setInterval` of its own

`totalSeconds`, `remainingSeconds` and `status` are plain controlled props, the same "component supplies the mechanism, caller supplies the state" split every stateful pattern in this epic already uses (`ConfirmDialog`'s `pending`, `FormDialog`'s `pending`/`error`). The actual tick belongs to whatever owns the real focus session — a future `useFocusSession`-shaped hook, not this component — which only ever renders whatever second it is told. The catalog demo owns a real `setTimeout`-driven countdown for exactly this reason: that ticking logic is the caller's responsibility to demonstrate, not this component's to provide.

### Tabular numerals for free, not re-implemented

The running clock (`formatClock`, a local `MM:SS`/`H:MM:SS` pure function — deliberately not `Intl.DurationFormat`, unsafe against this project's frozen Safari/Firefox target per the same reasoning `lib/duration.ts` already documents) renders through `ProgressRing`'s own `centerText` prop, which already carries `--lifeos-font-numeric` on that span. No new CSS was needed for the ticket's "tabular numerals" requirement — composing the right prop was the entire implementation.

### Only status transitions are announced — never the countdown

`useAnnouncer`'s own doc comment names the exact failure this guards against: "a value that updates often … writes to a live region every time it changes, and a screen-reader user hears a stream of interruptions with no way to stop it. The tone guide forbids announcing timer ticks … for exactly this reason." A `useEffect` watches only `status` (via a ref holding the previous value, so identical re-renders — including every `remainingSeconds` tick — announce nothing) and announces paused/resumed/completed exactly once per real transition. `remainingSeconds` is never read inside that effect.

### Pause/completed variants

`status` drives three visibly distinct things at once: which `ProgressTone` the ring uses (`running`/`idle` → primary, `paused` → warning, `completed` → success), the state text below the ring ("Ready"/"Running"/"Paused"/"Completed"), and which action buttons render — a button is shown only when both its status is active *and* the caller supplied that handler prop (`onStart` while idle, `onPause` while running, `onResume` and `onReset` while paused, `onReset` while completed), the same "no handler, no button" convention `FormDialog`'s actions already use.

### Reduced motion

A gentle opacity pulse on the ring itself (not a separate spinner) is the only visual cue that a value updating once a second is actually "live" rather than a static, static-looking display — the state text and the ring's own value already say "Running" in words, so the pulse's only job is the ambient "still going" signal, not information. `prefers-reduced-motion: reduce` disables it entirely (`animation: none`), matching the identical belt-and-suspenders pattern `ProgressRing`'s own transition and `SearchField`'s loading spinner already use, on top of the global token-level zeroing `styles/tokens.css` already applies to every `--lifeos-motion-duration-*` custom property. Not independently toggled live in this session — the available browser tooling has no way to emulate `prefers-reduced-motion` — but the rule is textually identical to two already-proven precedents.

## Known limitations or follow-ups

- No built-in overtime/negative display — `remainingSeconds` below `0` or above `totalSeconds` is clamped for rendering rather than shown as an over-time state. A screen wanting a "ran past its target" indicator would need to build that from the caller's own `status`/values, since the ticket does not name overtime as a required variant.
- `locale` is required rather than read from the browser, matching `DurationField`'s own precedent (`29-PRODUCT-VOCABULARY.md`/`DEPENDENCY-POLICY.md` favor deterministic, testable formatting over `navigator.language`).
