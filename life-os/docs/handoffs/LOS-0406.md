## Completed behavior

Adds `DurationField` to `apps/web/src/components/forms/`: two `NumberInput`s — Hours and Minutes — over one canonical total in minutes, matching the vocabulary doc's Estimate definition ("stored in minutes"). A new `lib/duration.ts` owns every conversion between the split shown on screen and the total actually stored, so the two representations can never drift apart.

### Normalization comes from deriving, not from special-casing

The two `NumberInput`s hold no state of their own — on every render they are computed fresh from `value` via `toDurationParts`, the same shape `DateRangeField` and `DateTimeField` already use for their own paired fields. That is what makes normalization automatic: typing `90` into Minutes while Hours reads `1` produces a total of 150 the instant it happens, and the very next render re-splits that into Hours `2`, Minutes `30`. There is no intermediate "1h 90m" state to detect and clean up, because the malformed shape is never what gets stored — only the corrected one.

### Bounds are reported, not rewritten — a real bug, not a hypothetical one

The first version of this field clamped the combined total to `min`/`max` on every keystroke, the same instinct that made sense for `NumberInput`'s own native attributes. It shipped two failing tests before it shipped anything else: clearing Minutes below a configured `min` snapped the field straight back to the floor value *while the user was still mid-edit*, and the next digit they typed landed appended to that snapped-back number instead of replacing it (a `min={15}` field cleared and typed `5` into ended up at `155`, not `15`). Live-clamping a controlled value out from under an in-progress keystroke is exactly the failure mode `NumberInput`'s own docstring already warns about for reformatting while typing — this ticket just found the concrete case.

The fix follows the same shape `DateRangeField`'s order check and `DateTimeField`'s daylight-saving check already use: derive whether the current value is out of range and say so with a message naming the correction (`"Enter a duration of at least 15 minutes."`), rather than substituting a different number than the one the user typed. The value the caller receives is always exactly what was typed; `min`/`max` never rewrite it. Each `NumberInput`'s own native `min`/`max` stays set as a best-effort constraint on top of that — the same layered pattern used everywhere else — but it is no longer the thing actually enforcing anything.

### The readable summary uses `Intl.NumberFormat`'s `unit` style, not `Intl.DurationFormat`

`formatDurationMinutes` produces both forms the tone guide asks for: compact ("1 hr 30 min") for dense UI, and long ("1 hour 30 minutes") carried in a `VisuallyHidden` span for assistive technology, so a sighted and a screen-reader user get the same information without the compact form's abbreviations being read aloud awkwardly. `Intl.DurationFormat` would produce this more directly in one call, but it is newer than this project's frozen browser target (`browserslist`: Safari ≥16.4, Firefox ≥114) can safely rely on; `Intl.NumberFormat`'s `unit` style has been supported since Safari 14.1 and Firefox 88, well inside it. Pluralization and localization come from Intl rather than a hand-rolled `${n} hour${n === 1 ? "" : "s"}`, matching the tone guide's explicit rule against appending `s` in code.

## Known limitations or follow-ups

- The whole-duration "Clear duration" action is a plain labelled button beside the pair rather than an icon inside either input's own shell, because there is no meaningful way to "half-clear" a duration the way `DateTimeField` clears its date and time independently. Styled to match `DateRangeField`'s own preset-button pattern rather than introducing a third small-button style.
- `formatDurationMinutes`'s compact form reads "1 hr 30 min" (ICU's own abbreviation) rather than the "1 h 30 min" shown as an illustrative example in the tone guide; using the platform's built-in, correctly localized abbreviation was judged more valuable than matching that one example's exact glyph.
- No days/weeks tier — the field is scoped to hours and minutes, matching Estimate's own definition. A feature needing a longer horizon (a Sprint's capacity, say) is out of this ticket's scope.
