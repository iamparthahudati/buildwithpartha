# LOS-0502 handoff

- Status: Done
- Branch: `feature/LOS-0502-password-policy-hashing`
- Date: 2026-08-18

## Completed behavior

Added password policy and Argon2id hashing on top of LOS-0501's `credentials` table, as the first real code in `auth.domain`/`auth.application`/`auth.infrastructure` — proving out the LOS-0206 layering (`PackageBoundaryRules`) for an actual business domain rather than just its ArchUnit fixtures.

- `auth.domain` (no Spring/JPA dependency, enforced by `layerDirection()`):
  - `EmailAddress` — NFC-normalize then lower-case, matching `users.email_normalized`.
  - `RawPassword` — wraps the plaintext just long enough to validate/hash it; `toString()` is redacted (`RawPassword[REDACTED]`) so a log line or an AssertJ failure message can never print the value.
  - `PasswordPolicy` — pure length check (`MIN_LENGTH` 12, `MAX_LENGTH` 128), per `06-SECURITY.md`'s length-over-complexity/no-periodic-reset stance (NIST SP 800-63B).
  - `CommonPasswordChecker` / `PasswordHasher` — ports so the domain and `auth.application` never import Spring or a specific hashing library.
  - `PasswordVerification` — the rehash-on-login result: `matched` plus an `Optional<String> rehashedHash`, structurally forbidden to carry a rehash on a failed match (constructor guard, tested).
- `auth.application`:
  - `PasswordService` — combines `PasswordPolicy.checkLength` and `CommonPasswordChecker.isCommon` into one `PasswordValidationResult`, and hashes via the `PasswordHasher` port.
  - `PasswordAuthenticationService.verify(rawPassword, storedHash)` — the rehash-on-login path the ticket names: verifies once, and only when the password matches *and* the stored hash's own embedded parameters are weaker than current (`PasswordHasher.needsRehash`, backed by `PasswordEncoder.upgradeEncoding`) does it compute and return the replacement hash. A future login (LOS-0505) persists it in the same transaction; it does not hash a second time on every login.
- `auth.infrastructure`:
  - `Argon2PasswordHasher` — `Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()`: 16-byte salt, 32-byte hash, parallelism 1, 16 MiB memory, 2 iterations (confirmed by decoding a sample hash: `$argon2id$v=19$m=16384,t=2,p=1$...`), in the range OWASP's Password Storage Cheat Sheet recommends for Argon2id.
  - `WordlistCommonPasswordChecker` — case-insensitive lookup against `src/main/resources/auth/common-passwords.txt`, a bundled ~300-entry list, satisfying `06-SECURITY.md`'s "breached/common-password screening where feasible" without a network call to a third-party breach API (which would also mean sending password material off-box).

- Added 10 test classes under `auth/domain`, `auth/application`, `auth/infrastructure`, plus `auth/PasswordWiringIT.java` (full `@SpringBootTest` proving Spring wires the real Argon2id/wordlist adapters, not only the fakes the unit tests use) and two hand-written test doubles (`FakePasswordHasher`, `FakeCommonPasswordChecker` — no mocking framework is a dependency of this project).
- `build.gradle.kts` — added `runtimeOnly("org.bouncycastle:bcprov-jdk18on:1.79")`. `spring-security-crypto` declares Bouncy Castle `compileOnly`; without it, hashing threw `NoClassDefFoundError: org/bouncycastle/crypto/params/Argon2Parameters$Builder` at runtime, caught immediately by the test suite.
- `gradle.lockfile` — regenerated (`--write-locks`) to include the new dependency.

## Known limitations or follow-ups

- No signup/login API, `Credentials` JPA entity, or repository exists yet — this ticket is deliberately just the reusable policy/hashing service, per its own acceptance contract. LOS-0503 (signup) and LOS-0505 (login) wire these services to real persistence.
- The common-password list is a small curated set (~300 entries), not a full breach corpus; broadening it (or adding an offline k-anonymity HIBP dataset) is a reasonable future hardening, not required by this ticket's "where feasible" wording.
- This environment's Gradle daemon defaults to a JDK 17 JVM even though the project's toolchain targets 21, which made `spotlessApply`/`spotlessCheck` fail with an unrelated `google-java-format` `InvocationTargetException` on every file (old and new) until invoked with `JAVA_HOME` pointed at a JDK 21 install. Not caused by this ticket; worth a `gradle.properties` fix in a dedicated ticket if it recurs for other contributors.
