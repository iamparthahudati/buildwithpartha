## Completed behavior

Adds `AttachmentUploader` and `AttachmentList` to `components/navigation/` — a feature-flagged file picker plus the list of what it's picked, together covering the ticket's full "picker, restrictions, progress/cancel/retry, safe filename, scan state and authorized download/delete UI" contract.

### The Files capability is `docs/31`'s one P4 "optional high-risk" feature, and the component says so

`docs/31-PRIVACY-DATA-LIFECYCLE.md` keeps attachments off "until dedicated threat/privacy/processor review and explicit notice/control." `AttachmentUploader` takes a real `enabled` prop for exactly this: `false` renders the tone guide's own exact copy (`Attachments aren't enabled for LifeOS yet.`) instead of hiding silently, since a caller that already decided to show an attachments section still needs to explain why it's empty.

### `status` walks the privacy doc's own scan lifecycle, not an invented one

`AttachmentStatus` is `uploading` (bytes in flight, cancellable) → `scanning` ("scan before availability" — a file is never downloadable the instant its upload finishes) → `ready` (clean, authorized actions available) or `blocked` (failed the scan; never offered for download), with a separate `failed` (the upload itself didn't complete; retryable) off the `uploading` branch. `AttachmentList` performs none of the upload or the scan itself — the same controlled, caller-owns-the-state split `ConfirmDialog`'s `pending` and `TimerRing`'s own ticking already use in this epic.

### Authorization is gated by callback presence, not a disabled button

`onDownload`/`onDelete` decide whether their own controls render at all. `AGENTS.md`'s non-negotiable rule is that authorization is enforced by the backend, never only by a hidden frontend control — a caller that already knows a record isn't downloadable/deletable for this Account has nothing useful to disable, because there is no button that should exist to begin with.

### Delete reuses `ConfirmDialog` (LOS-0413) internally and closes itself on success

The same destructive-action-needs-its-own-dialog shape `Drawer`'s `isDirty` guard (LOS-0414) already established: the dialog names the exact file being removed (`Delete "Signed contract.pdf"?`), and `deletePending`/`deleteError` pass straight through to `ConfirmDialog`'s own identical props. The dialog closes itself once the caller's own successful delete removes the target from `attachments` — a render-time state adjustment, the same one `ConfirmDialog` already uses to reset its typed-confirmation field on reopen — rather than a separate `onDeleted` callback the caller would otherwise have to remember to call.

### A real spoofing technique, neutralized before display

A crafted filename can embed a Unicode bidi override character (U+202E, "right-to-left override") to visually reverse its own extension — bytes reading `gpj.exe` displayed as `exe.jpg` — a real, documented technique, not a theoretical one. `sanitizeFileNameForDisplay` strips the nine bidi control code points before any filename reaches the DOM, built from numeric code points rather than a regex literal so the source file itself never has to carry an invisible override character to match one. This only changes what is shown; nothing about what is stored or uploaded.

### Restriction and progress copy come straight from the tone guide's own table

`Choose a {allowedTypes} file up to {maximumSize}.` is `AttachmentUploader`'s one message, serving as both the standing hint and the rejection notice — the tone guide names an identical "Unsupported file" message regardless of which restriction failed, so there is no second sentence to invent. `Uploading {fileName}: {percentage}%` is `AttachmentList`'s `aria-valuetext` on the in-flight row, verbatim from the same table.

## Known limitations or follow-ups

- No drag-and-drop onto the picker — the ticket names a "picker," and a drop zone is an additive interaction a screen can layer on top of the same `onFilesSelected` contract later, not something this ticket's wording requires.
- No thumbnail/preview rendering for image attachments — `fileName`/`fileSizeBytes`/`status` is the full row contract; a screen wanting an image preview would need its own authorized preview URL, out of scope for the picker/list primitive itself.
- `AttachmentList` handles one delete at a time by construction (a single `deleteTargetId`), matching how its one internal `ConfirmDialog` can only ever confirm one action; a caller batch-deleting many attachments at once would need its own bulk-action affordance, the same escape hatch `DataTable`'s `selection.bulkActions` already uses.
