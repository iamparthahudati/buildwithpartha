## Completed behavior

Adds `Pagination` to `components/navigation/`, plus a standalone pure function, `paginationRange.ts`.

### A real nav of real buttons, with real disabled boundaries

`<nav aria-label={label}>` wraps real `<button>` page controls, each with an explicit `aria-label="Page N"` since a bare number is not a self-explanatory accessible name out of context. The current page carries `aria-current="page"` (announced, not only styled) alongside its own visual treatment. Previous and Next are genuinely `disabled` at the real first/last page — not merely styled to look inert, which would leave a keyboard user able to tab to and activate a control that does nothing.

### `paginationRange` collapses two gaps, not one

`breadcrumbsCollapse.ts` (LOS-0417) has a single collapse point: everything between a fixed head and tail. Pagination needs two — a gap can open on *either* side of the current page depending on where it sits in a long list, and both the first and last page must stay reachable in one click regardless of how far into the list the user has navigated. `paginationRange(page, totalPages, siblingCount = 1)` is the pure function that decides this: it always keeps the first and last page, keeps `siblingCount` pages on each side of the current page, and replaces whatever falls outside that with a single ellipsis marker per gap. The three shapes (collapse only the right side near the start, collapse only the left side near the end, collapse both sides in the middle) are each covered by their own test, along with the "never emit a page number outside `[1, totalPages]`" invariant and a wider `siblingCount`.

Confirmed live in a browser, not only in the pure-function tests: clicking page 5 in a 20-page demo re-rendered the visible set to `1 … 4 5 6 … 20`, matching what the pure function predicts for that exact input.

### `page`/`onPageChange` is a plain controlled pair — "URL integration" is the caller's choice

Same shape `Tabs` (LOS-0416) already established for its own "local versus URL-synced" split: `Pagination` has no opinion on whether the caller backs `page` with `useState` (forgotten on reload) or `useDeepLinkParam` (LOS-0414, survives one and integrates with the browser's Back button). The catalog demonstrates both side by side. Confirmed live: clicking a page number in the URL-synced demo changed `window.location.search` to `?catalog-page=3` for real, not just updated component state.

## Known limitations or follow-ups

- No page-size selector. The ticket's "Page/size/total" is read as the three numeric inputs `Pagination` needs to compute page boundaries (`page`, `pageSize`, `total`), not an interactive page-size-changing control; a screen wanting one composes its own alongside `Pagination`, the same way `FilterBar` (LOS-0420) leaves its own filter fields to the caller.
- The compact mobile label ("Page X of Y") is read-only text, not itself a jump-to-page control — Previous/Next remain the only navigation on a narrow viewport, matching the ticket's literal "compact mobile variant" rather than adding a second interaction surface.
