## Completed behavior

Adds `Combobox` to `apps/web/src/components/forms/`: an accessible single/multi-select built on a real text input, following the ARIA 1.2 combobox-with-listbox pattern. `Select` (LOS-0317) stays the default; this exists only for free-text filtering across many options, multiple selection, or letting the user create an option that does not exist yet.

### Focus never leaves the input

The input keeps real DOM focus at all times; `aria-activedescendant` — not focus — points at whichever option the keyboard is currently on. Moving focus into the listbox itself is the older, more fragile ARIA pattern. Every option row carries `onClick` with no co-located keyboard handler, which is correct here (justified inline with an eslint-disable) rather than a gap: the option is never a keyboard target, the input's own `onKeyDown` drives every keyboard path.

`activeIndex` is stored as raw state, but nothing downstream reads it directly — a derived `activeVisibleIndex` (clamped against the current, possibly-just-narrowed list) is what actually renders and drives `aria-activedescendant`. An effect that wrote the clamp back into state would just cause an extra render to reach the same value, and the lint rule for exactly that pattern (`react-hooks/set-state-in-effect`) is what caught it during this ticket.

### An empty listbox is invalid ARIA, twice over

Two real accessibility bugs came from the loading/no-results/create rows, both caught by the axe sweep during development, not designed around up front:

1. A `role="listbox"` with zero `role="option"` children — the no-results state, or the moment loading starts before any options have arrived — fails `aria-required-children`. Fixed by only applying `role="listbox"` (and its `aria-label`/`aria-multiselectable`) to the `<ul>` once it actually owns at least one option or create row; the element itself always exists at the same id while open, so the input's `aria-controls` never points at a ghost id.
2. Once the `<ul>` stopped being a listbox in that case, its status `<li>`s could no longer carry `role="presentation"` either — a presentation-role item inside a *plain* list breaks the list's own required listitem content exactly as badly as an empty listbox does. The role on each status row is now conditional on whether the surrounding list currently *is* a listbox.

### Multi-select stays open; chips get a real tab stop

Selecting an option in multi-select mode leaves the listbox open — closing it after the first pick would undo the entire point of choosing more than one. Selected values render as removable chips before the input. Each chip's dismiss button is a normal tab stop, not `tabIndex={-1}` the way `TextInput`'s clear button is: a text field's clear has an obvious keyboard equivalent (select all, delete), but there is no keyboard equivalent for removing one arbitrary chip out of several, so it needs its own reachable control. Backspace against an empty query removes the most recently added chip as a well-known tag-input shortcut — a bonus, not a replacement for the per-chip button.

### Virtualize threshold, honestly scoped

Beyond `virtualizeThreshold` (default 50) matches, only the first N render and a status row explains the rest are narrowed by typing. This is **not** DOM virtualization — no windowing library exists in this project, and adding one is a dependency decision this ticket does not make per `docs/DEPENDENCY-POLICY.md`. It is the same honest limit on what actually renders, documented as such in the prop's own comment rather than claimed as something it is not.

### `fieldIds` joins the frozen public API

`Combobox` needed the same id-generation helper every other Field-based atom already uses internally. It was private to `components/ui` before this ticket; exporting it from `components/ui/index.ts` is a **purely additive** change to the LOS-0333 frozen API (no existing export's contract changed), made to avoid rebuilding the same utility a second time inside `components/forms`. Recorded here per the phase gate's instruction to record any change to the frozen surface rather than let it pass silently — an ADR was judged unnecessary for a backward-compatible addition, but the reasoning belongs in the historical record either way.

## Known limitations or follow-ups

- Local filtering is always substring-on-label; a caller doing server-side/async filtering should pass already-relevant `options` for the current `query` — the local filter then acts as a harmless no-op safety net over an already-narrow list, not a second competing filter.
- No hover-driven active-option sync: only the keyboard and explicit clicks set the active/selected state. This keeps the interaction model simple and was a deliberate scope cut, not an oversight.
- The listbox does not reposition on scroll/resize while open, matching `Tooltip`'s (LOS-0326) same accepted limitation.
- No feature yet wires `Combobox` to a real API; `loading`/`onCreateOption` are exercised only by the catalog's local state in this ticket.
