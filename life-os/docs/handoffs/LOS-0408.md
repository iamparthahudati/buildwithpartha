## Completed behavior

Adds `Alert` and `InlineMessage` to `apps/web/src/components/feedback/` — the first ticket to populate that shared category; `feedback/index.ts` had stood as a placeholder (`export {};`) since `STRUCTURE.md` first reserved it. Both share one four-tone contract (`MessageTone`, new in `scales.ts`: info/success/warning/danger) and one icon per tone (`messageContract.ts`), so a problem reads the same way whether it is a full page banner or three words beside a control. `InlineMessage` is the icon-plus-colored-text shape `FieldMessages` already draws for one field's error, generalized for anywhere else that needs it; `Alert` is the same contract with room for a heading, an action and a dismiss control.

### Role selection is the caller's decision, not the tone's

The ticket's "role selection preventing duplicate announcements" requirement, and the tone guide's own explicit rule ("Do not show a success toast and a duplicate inline success message unless one serves a distinct accessibility/context purpose"), both point at the same real failure mode: a component that gives every instance of a tone the same live-region role will over-announce whichever half of its uses doesn't want one. A `danger`-toned message reading "This account is suspended" is permanent page content; one reading "Save failed" exists *because* a save just failed. Only the caller knows which is true for a given render, so `announce` (`"none" | "status" | "alert"`, new `MessageAnnouncement` type) is an explicit prop on both components rather than something derived from `tone`, and it **defaults to `"none"`** — the safest option, since an unwanted interruption is worse for a screen-reader user than a message that is simply present and read in normal document order.

Both components' tests include a regression specifically named in the ticket: rerendering the *same* `Alert`/`InlineMessage` with new message content (the realistic case — a second validation failure replacing the first, still inside an `announce="alert"` region) must update the existing DOM node in place rather than tear it down and rebuild it. React's own reconciliation already provides this as long as nothing gives the element a changing `key`; neither component does, and the test asserts the outer node's identity is unchanged across the rerender. A remount here is exactly what would cause most screen readers to treat a still-visible message as freshly inserted content and announce it a second time for no new reason — the concrete version of "duplicate announcements" this ticket is aimed at.
