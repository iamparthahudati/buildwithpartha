## Completed behavior

Adds `PageHeader` to `components/navigation/`, composing three pieces this epic already built: `Breadcrumbs` (LOS-0417), `Heading` (LOS-0305) and `Menu` (LOS-0415).

### One header, one real `<h1>`

`title` is always rendered as `<Heading level={1}>` — unlike `Heading` itself, whose whole point (per its own LOS-0305 docstring) is that level and visual size vary independently for every other heading in the app, `PageHeader` has no `level` prop at all. A page header owns exactly one document-outline-defining title; making that configurable would just let a caller build a page with zero or two `<h1>`s by mistake.

### "Primary/split actions" read as a layout split, not a split-button widget

The ticket's wording is genuinely ambiguous between two real UI patterns: a "split button" (one control, a primary click area and a chevron that opens a menu of variants of the *same* action) and a layout that splits the primary action from a set of secondary ones. This implementation is the second: `primaryAction` renders as-is (typically a `Button`), and `secondaryActions` — a `MenuItemDescriptor[]`, `Menu`'s own item type — render behind a single `IconButton` (`MoreHorizontal`, labelled "More actions") that opens a `Menu`. Reusing `Menu` directly rather than building a second dropdown pattern was the deciding factor: it needed no new keyboard handling, no new collision logic, and no new tests for behavior `Menu` already proves — only the composition itself needed testing.

### Metadata and description stay caller content

`description?: string` and `metadata?: ReactNode` are both optional and both entirely caller-supplied, matching the "component supplies structure, caller supplies copy" rule this design system uses everywhere (`EmptyState`, `ErrorState`, `AccountMenu`'s identity block). `metadata` is typed as `ReactNode` rather than a fixed shape because what belongs there — a status badge, a `StatusDot` row, an owner avatar — genuinely varies by screen, and inventing a structured prop for it would just be a worse, narrower version of "pass children."

### Responsive wrapping, confirmed against real measured layout

The title block and the actions sit in one flex row (`justify-content: space-between`) that wraps once it cannot fit both; below the 768px breakpoint, `.lifeos-page-header__actions` additionally takes `width: 100%`, forcing it onto its own row under the title block rather than merely wrapping wherever there happens to be room — automatic by breakpoint, the same "responsive" every other composed component in this design system already uses. This was confirmed live, not just read off the CSS: resizing the browser to a 375px mobile viewport and comparing `getBoundingClientRect()` for the title block and the actions row showed the actions row's `top` sitting below the title block's `bottom`, and its width matching the available viewport width — the actual computed layout, not an assumption about what the media query does.

## Known limitations or follow-ups

- No true "split button" variant (one control, primary click plus a chevron opening variants of the same action) — if a future screen needs that specific pattern, it is a different composition, not an option on this component.
- `secondaryActions` accepts exactly `Menu`'s own `MenuItemDescriptor[]`, so anything `Menu` cannot yet express (a submenu, for instance) is also unavailable here; this is a direct, deliberate consequence of reusing `Menu` rather than a limitation specific to `PageHeader`.
