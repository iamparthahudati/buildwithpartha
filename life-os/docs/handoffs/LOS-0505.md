- Status: Done

## Completed behavior

Added `POST /auth/login`, plus the session-authentication mechanism that makes the session it issues actually mean something to the rest of the API — the largest ticket in the epic so far, matching signup's own 8-hour estimate.

- `auth.domain.Session` mirrors `EmailVerificationToken`'s "only the hash is ever persisted" shape for `public.user_sessions`, with a login-time engineering default `TTL` of 30 days (no "remember me" checkbox exists, so every session gets the same duration) and an `isActive(Instant now)` check (`revokedAt` empty and not yet expired).
- `auth.application.LoginService.login` is one `@Transactional` method: rate limit, look up the account by normalized email, require `AccountStatus.ACTIVE`, verify the password (`PasswordAuthenticationService`, LOS-0502 — including its rehash-on-login path, applied and persisted in the same transaction), then issue a **brand-new** `Session` unconditionally. Every rejection reason — unknown email, an account that exists but is not yet verified, or a wrong password — throws the exact same `InvalidCredentialsException` with the exact same message, matching `06-SECURITY.md`'s "Generic auth recovery responses prevent account enumeration" the same way LOS-0503's duplicate-signup handling already does; a caller cannot use login itself to probe which emails have accounts.
- **Session fixation**: `LoginService` never reads or reuses an incoming session cookie — it has no way to, since nothing about the request's existing cookie state ever reaches it. A session is always newly minted with a fresh `UUID`/token/hash, proven by a test asserting two logins for the same account produce two different session rows.
- **CSRF bootstrap**: a second `SecureTokenGenerator`-minted `RawToken` is generated per login; its hash is stored as the session's `csrf_secret` (an existing LOS-0501 column — "never echoed in an API response" refers to that stored hash, exactly like `token_hash`) and its raw value is returned once, in the login response body only. `SecureTokenGenerator` gained `hash(String rawValue)` in LOS-0504 specifically so a caller-presented value can be re-hashed and looked up rather than decrypted; this ticket is its second real use.
- `SessionAuthenticationFilter` (`config`, not `auth.infrastructure` — it wires directly into `ApiSecurityConfiguration`'s `SecurityFilterChain`) is the counterpart LOS-0505 also had to build: without it, `.anyRequest().authenticated()` (already active since LOS-0213) could never succeed for anything, making the whole login feature untestable end-to-end. It reads the `lifeos_session` cookie, re-hashes it, looks up the session, and — only if `isActive` — authenticates the request with the session's `userId` as a raw principal (`06-SECURITY.md`: "controllers do not accept a user ID for ownership"; a future controller reads it via `@AuthenticationPrincipal UUID`). Registered with `HttpSecurity.addFilterBefore(..., AuthorizationFilter.class)`, not `@Component`: a bare component-registered filter runs outside Spring Security's own chain and its `SecurityContextHolder` write could be silently overwritten by Security's own context-loading step.
- `AuthController.login` builds the `Set-Cookie` header inline (`ResponseCookie`: `HttpOnly`, `Secure` driven by `LifeOsEnvironmentProperties.sessionCookieSecure` — provisioned back in LOS-0202/0211 specifically for this, `SameSite=Lax`, `Path=/life-os`, `Max-Age` matching `Session.TTL`) and returns the safe user fields plus the CSRF bootstrap value in the body. The session token itself never appears in the response body.
- `device_hint` (deferred to this ticket by LOS-0501's own column comment) is the request's `User-Agent` header, capped at 255 characters, `Optional.empty()` when absent — an opaque troubleshooting string, not parsed or structured.
- CSRF header *enforcement* (rejecting a mutation without a matching `X-CSRF-TOKEN`) is explicitly **not** built here: nothing in the app has an authenticated mutating endpoint to protect yet. That belongs to LOS-0506 (logout), whose own acceptance line already says "require CSRF as applicable."

## Known limitations or follow-ups

- No `POST /auth/logout` or session revocation exists yet — LOS-0506's job, including clearing the cookie this ticket sets and enforcing the `X-CSRF-TOKEN` header this ticket only bootstraps.
- No "list/revoke my other sessions" capability exists (`06-SECURITY.md`: "Provide session listing and 'sign out all devices'"); that is LOS-0516's job per the backlog, on top of LOS-0506.
- `InMemoryLoginRateLimiter` is IP-address-only, the same single-instance, non-evicting, narrow placeholder shape `InMemorySignupRateLimiter` already established — `LOS-1401`'s general framework is expected to supersede it outright, and is also where a per-account (not just per-address) brute-force defense belongs, since IP-based limiting alone does not stop a slow, distributed attack against one account.
- If the frontend loses its in-memory CSRF token (e.g. a page reload) while the session cookie is still valid, there is currently no way to fetch a fresh one without re-entering the password — no `GET /auth/session` or `/auth/me` "session bootstrap" endpoint exists, and no ticket in `EPIC-05-IDENTITY.md` currently names one, even though LOS-0508's own acceptance line ("Frontend session bootstrap") appears to assume one exists. Worth flagging before LOS-0508 is picked up.
- `SessionAuthenticationFilter` does not update `last_seen_at` on use; it is written once at issuance and never touched again. Not required by this ticket's acceptance contract, but a future "show last active" feature (LOS-0516) will need it kept current.
- Expired sessions are never purged from `user_sessions` by a cleanup job (the table's own `ix_user_sessions_cleanup` partial index anticipates one); out of scope here, matching how LOS-1402's `OutboxCleanupJob` was its own ticket's job rather than being built speculatively earlier.
