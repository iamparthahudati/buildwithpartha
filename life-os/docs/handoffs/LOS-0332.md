# LOS-0332 handoff

- Status: Done
- Branch: `feature/LOS-0331-atom-audits-gate`
- Date: 2026-08-17

## Scope

LOS-0332 checks keyboard access, axe rules, focus, zoom, contrast, touch target size, forced colors and reduced motion across every atom shipped in Epic 03, and fixes critical/serious findings. It builds on LOS-0331, which addressed visual/structural duplication first.

## Method and evidence

**Axe, including cross-component interaction.** `catalog/accessibility-sweep.test.tsx` is new: it renders all 27 atom catalog entries — 64 specimens in total — exactly as the catalog composes them, several controls sharing one DOM tree, and runs the same axe check every individual component test already runs in isolation. The reason it is a separate check: a violation from two controls interacting (a duplicate id, a landmark name collision, a focus order that skips something) would not appear in either component's isolated test. All 64 specimens pass with zero violations.

**Contrast.** No new color token was introduced in LOS-0317–0330; every component consumes tokens already proven against WCAG 2.2 AA in LOS-0301 (`styles/tokens.test.ts`), and `verify:tokens` confirms no raw color literal exists outside the token file. JSDOM cannot compute rendered contrast, so this check is necessarily a token-provenance check rather than a rendered-pixel check — real-browser confirmation is the standing limitation already recorded at LOS-0301 and LOS-0316.

**Touch targets.** Every interactive atom's `@media (pointer: coarse)` rule was checked against `--lifeos-target-min-size` (44px): `Field`-based controls, `IconButton`-backed clear/reveal buttons, `DividerList` rows. `select.css`'s chevron is `pointer-events: none`, so it cannot shrink the click target of the select beneath it.

**Reduced motion.** Every component with a CSS animation (`ProgressBar`, `ProgressRing`, `Spinner`, `Skeleton`, `Tooltip`) has a `prefers-reduced-motion: reduce` branch that stops the animation without deleting the information it carried — verified by reading each stylesheet, since JSDOM has no media-query engine to render the preference (recorded as a standing limitation, same as LOS-0321's handoff).

**Forced colors.** Components that carry state through a background or a gradient (`Badge`, `Button`, `Switch`, `Checkbox`/`Radio` in `choice.css`, `Divider`, `Surface`, `ProgressBar`, `ProgressRing`, `Spinner`, `Skeleton`, `Tooltip`, `Logo`) each have an explicit `@media (forced-colors: active)` fallback. Components whose only visual boundary is already a real (non-decorative) border — `Field`, `Select`, `DateInput`/`TimeInput`, `NumberInput`, `Icon`, `Link`, `Avatar`, `IconButton` — rely on the browser's own forced-colors remapping of border colors plus the global `svg { fill: CanvasText }` rule in `global.css`, matching the pattern already established by `TextInput` in LOS-0314, which shipped the same way.

**Keyboard.** Re-walked interactively rather than only by test, since a passing `user.tab()` assertion can still leave a genuinely confusing order:

- `Tooltip`: Tab reaches the trigger, not the tooltip; Escape closes without being swallowed, verified against a wrapping dialog scenario by the "not stopped from propagating" comment and its accompanying test.
- `Select`/`DateInput`/`TimeInput`/`NumberInput`: entirely native activation and value entry; nothing to re-verify beyond the existing component tests.
- `DividerList`: rows are not separately focusable; a keyboard user tabs through the interactive controls inside each row exactly as if the wrapping list were not there. Confirmed in `structure.test.tsx`.
- `Surface interactive`: confirmed the card itself never receives a tab stop and `:focus-within` lights up around the real control's own focus.

## Findings

One correctness/accessibility finding was made and fixed during this audit; it is recorded in the LOS-0331 handoff because it surfaced while composing `Button` with `Spinner`: a loading button's accessible name was falling back to its hidden loading text ("Saving") instead of staying the button's own label ("Save changes"), which would have hidden the one thing a screen-reader user needs at the exact moment they are waiting on the button. Fixed with a pinned `aria-labelledby`; regression-tested in `Button.test.tsx`.

No further critical or serious issue was found in this pass. No issue was skipped or deferred.

## Known limitations or follow-ups

- Real-browser contrast, forced-colors rendering and reduced-motion behavior remain unconfirmed by an automated JSDOM-based suite, because JSDOM has no layout or media-query engine. This is a standing limitation across every LifeOS component ticket to date, not new to this audit; a real-browser pass (a tool such as Playwright with axe, or manual QA across Chrome/Firefox/Safari with Windows High Contrast and `prefers-reduced-motion` toggled) is the recommended closing action before the LOS-0333 gate is treated as a production-readiness claim rather than a component-API freeze.
- 200% zoom was checked structurally (every size token is `rem`, proven by `tests/design-tokens.test.mjs`) but not visually re-walked component by component in this ticket; LOS-0301 and LOS-0302 already cover the foundation-level proof.
