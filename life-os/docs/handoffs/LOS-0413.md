## Completed behavior

Adds `ConfirmDialog` to `apps/web/src/components/feedback/`, built on `Dialog` (LOS-0412). It exists only for an irreversible or high-impact action — the tone guide is explicit that a reversible one prefers `Undo` (a `Toast` action slot) instead, and that `Undo` never substitutes for confirming one that genuinely can't be taken back.

### `description` and `confirmLabel` are required, not stylistic choices

The tone guide states plainly: "The dialog must name the record and exact consequence. Button labels repeat the action," and separately prohibits generic `Are you sure?`, `Yes`, `Proceed` and misleading `Remove`. Making `description` and `confirmLabel` **required props** (not optional with a fallback) is what turns that rule into something a caller cannot accidentally skip — a `ConfirmDialog` with no description or a button labelled "Confirm" is a type error here, the same enforcement technique `IconButton`'s required `label` and `DateTimeField`'s required `timeZone` already use for their own must-not-skip rules.

### State stays the caller's — no internal async, on purpose

`onConfirm` is a plain `() => void`, and `pending`/`error` are controlled props, not something `ConfirmDialog` awaits or catches itself. This matches every composed field in this design system (`DateTimeField`, `DurationField`, `ColorIconPicker`, `Toast`'s own queue) — none of them run internal async orchestration; the caller owns the state transition. The alternative — `ConfirmDialog` wrapping `onConfirm` in its own try/catch — would require it to invent a generic failure message for an arbitrary thrown value, exactly the kind of copy this design system consistently refuses to invent internally, and would leave the caller with no way to distinguish "still in flight" from "already committed" if the two states ever needed different handling.

### Default focus goes to Cancel, not the close button and not the danger action

`Dialog`'s own default (first focusable descendant) would land on its header's close button — an accident of DOM order, not a deliberate choice for a confirmation. `ConfirmDialog` sets `initialFocusRef` explicitly to the Cancel button, so an accidental Enter press on open cannot land on the destructive action. When `typedConfirmation` is present, focus goes to that field instead, since nothing else can be done until it's filled in — Cancel is still reachable by Tab, and the confirm button stays disabled either way until the text matches exactly.

### Typed confirmation resets state during render, not in an effect

A newer `react-hooks/set-state-in-effect` lint rule caught the first draft's `useEffect` that cleared the typed value on `open` becoming true — calling `setState` synchronously inside a plain effect risks a visible flash of the stale value before the reset commits. Fixed using React's own documented pattern for this exact situation — comparing the previous `open` value during render and adjusting state there — which is also simply the more correct fix, not a workaround for the lint rule.

## Known limitations or follow-ups

- No built-in retry-count or backoff; `pending`/`error` are single-shot controlled props and a caller wanting rate-limited retry (the tone guide's `Too many attempts. Try again in {duration}.` case) composes that themselves using the same props.
- Account deletion's specific copy (sign-out effect, grace period, cancellation path, purge boundary, backup retention) is explicitly deferred in the tone guide itself pending LOS-0113/implementation policy values — this ticket supplies the mechanism (`typedConfirmation`) that screen would use, not its copy.
- `typedConfirmation` compares the typed value with strict equality; no case-insensitive or trimmed-whitespace leniency, matching how the tone guide's own examples ("Type the project name to confirm") imply an exact match is the point of the exercise.
