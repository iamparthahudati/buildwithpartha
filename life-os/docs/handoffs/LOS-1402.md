## Completed behavior

Added the transactional outbox and mail worker that LOS-0503 (signup) and LOS-0507 (password reset) will depend on to send verification/reset/security mail reliably. No caller wires into it yet — that integration is explicitly out of scope here and lands with LOS-0503/LOS-0507 — but the full enqueue → dispatch → retry/backoff → dead-letter → cleanup path is built, tested, and ready.

Two architectural decisions were made explicitly (confirmed with the requester before implementation) because the codebase's ArchUnit rules don't leave them ambiguous by accident:

- **Package home**: built inside the existing `notification` domain (`auth, user, project, ... notification, audit` is `PackageBoundaryRules`' exhaustive `DOMAIN_PACKAGES` list) rather than a new top-level `mail`/`outbox` domain, which would have required editing that enumerated list. `notification`'s own `package-info.java` already read "Private notifications and reliable notification delivery coordination" — an exact fit, left unchanged.
- **Cross-domain contract**: added `common.mail` — a domain-neutral port (`TransactionalMailPort`) plus minimal value types (`MailMessageKind`, `MailRecipient`, `MailTemplateVariables`) — mirroring the existing `common.error`/`common.pagination` precedent. `notification.infrastructure.TransactionalMailPortAdapter` implements it. This exists so a future `auth.application` caller can enqueue mail without depending on any `notification` internals, satisfying `PackageBoundaryRules.domainIsolation()`.

Layers, matching the `auth` domain's established shape from LOS-0502:

- `notification.domain` (zero Spring/JPA): `OutboxMessage` (the aggregate — enqueue, `recordSuccess`, `recordFailure`, `isDueForDispatch`), `OutboxMessageStatus`, `RetryPolicy` (pure exponential backoff: 30s/60s/2m/4m/8m/16m/30m-capped, dead-letter at the 8th attempt, ~61 minutes total — fast first retry since verification/reset mail is time-sensitive, capped so a longer SMTP outage isn't hammered, no jitter since this is a single low-volume instance), ports `OutboxRepository`/`MailTransport`/`MailTemplateRenderer`, `RenderedMailMessage`, and two domain-only unchecked exceptions.
- `notification.application`: `MailOutboxService.enqueue(...)` — `@Transactional` with default (`REQUIRED`) propagation, so it joins the caller's own transaction; this is the actual "transactional" half of the pattern. `MailDispatchWorker` — `@Scheduled(fixedDelay = 15_000)` poller; single-instance deployment (`02-ARCHITECTURE.md`: one VPS, one Spring Boot service) means no row-leasing/`SKIP LOCKED` is needed, and `fixedDelay` (not `fixedRate`) guarantees non-overlapping polls. Each `save` is transactional per-call via Spring Data JPA's default, so one message's failure in a batch can't roll back another's success. Logs only message id/kind/status/attempt count/a sanitized exception **class name** — never the raw exception message, template variables, or rendered body. `OutboxCleanupJob` — daily, purges terminal (`SENT`/`DEAD_LETTERED`) rows older than 7 days, matching retention class R1 in `31-PRIVACY-DATA-LIFECYCLE.md` ("purge expired/consumed records within 7 days... failed job payloads after resolution"). Kept in this ticket's scope rather than deferred to LOS-1403, since the privacy doc ties the obligation directly to the outbox's existence and the query needs none of LOS-1403's planned leasing/idempotency machinery.
- `notification.infrastructure`: `OutboxMessageEntity` (the project's first JPA `@Entity`) + `TemplateVariablesConverter` (a hand-rolled `AttributeConverter<Map<String,String>, String>` using `tools.jackson.databind.json.JsonMapper`, mapping to a plain `TEXT` column rather than pulling in a `jsonb` Hibernate-type dependency) + `OutboxMessageJpaRepository`/`JpaOutboxRepository`; `JavaMailSenderMailTransport` (adapts Spring's already-configured `JavaMailSender`; captures whatever `Message-ID` JavaMail assigns after send as the provider message id — plain SMTP has no server-assigned id to read back, and forcing a custom one would require overriding `MimeMessage.updateMessageID()`, not worth the complexity for a troubleshooting-only field); `ResourceMailTemplateRenderer` (bundled `{{var}}`-substitution plain-text templates, mirroring `WordlistCommonPasswordChecker`'s `ClassPathResource` pattern; plain text sidesteps needing to HTML-escape substituted values); `TransactionalMailPortAdapter` (the `common.mail.TransactionalMailPort` implementation).
- `config`: `SchedulingConfiguration` (`@EnableScheduling` — first use in the codebase) and `ClockConfiguration` (`Clock.systemUTC()` bean, first `Clock` bean in the codebase).

**A real correctness bug was found and fixed during verification, not just during coding**: Spring's default `@Scheduled` task scheduler uses non-daemon threads. Under `spring.main.web-application-type: none` (the profile `scripts/verify-flyway-postgres.sh` boots to validate the JPA entity against a real migrated schema), nothing else keeps the JVM alive once context startup finishes — so with no explicit `TaskScheduler` bean, the headless verification process hung forever instead of exiting after its checks completed. `SchedulingConfiguration` now provides an explicit `ThreadPoolTaskScheduler` bean with `setDaemon(true)`. This has no effect on the real web app (Tomcat's own acceptor threads already keep it alive) but makes any headless/CLI-style boot of this application exit cleanly, which is the behavior a script like this correctly assumes.

`OutboxMessage.templateVariables` (which may carry a raw verification/reset URL token) is wiped to `MailTemplateVariables.empty()` the instant a message reaches a terminal state (`recordSuccess`, or `recordFailure` once `RetryPolicy` is exhausted) — not just at the 7-day cleanup — matching `31-PRIVACY-DATA-LIFECYCLE.md`'s "outbox payloads are erased after delivery/final failure" line. A failure that will still be retried keeps the variables, since they're needed to re-render on the next attempt.

- Added `config/SchedulingConfiguration.java` (`@EnableScheduling` + daemon `TaskScheduler` bean) and `config/ClockConfiguration.java` (`Clock` bean).
- Added `db/migration/V3__outbox_schema.sql` — `outbox_messages` table: `message_kind`/`status` CHECK-constrained, `user_id` nullable `ON DELETE CASCADE`, a partial index for the due-message poll (`WHERE status = 'PENDING'`) and one for the R1 cleanup query (`WHERE status IN ('SENT','DEAD_LETTERED')`), following `V2__identity_schema.sql`'s exact constraint/index/comment conventions.
- Added bundled templates `src/main/resources/notification/templates/{email-verification,password-reset,security-alert}/{subject,body}.txt` — plain text with illustrative `{{var}}` placeholders; real copy/variable names are LOS-0503/LOS-0507/LOS-1404's job when they wire real callers.
- Added `src/test/resources/schema.sql` — **required**, not optional: this ticket adds the project's first JPA `@Entity`, and the `test` profile's H2 database runs `hibernate.ddl-auto: validate` with no prior schema-creation mechanism. Every full-context `@SpringBootTest` (including the pre-existing, unrelated `auth/PasswordWiringIT.java`) would otherwise fail at startup. Declared `CREATE TABLE IF NOT EXISTS` since more than one Spring context in the same test JVM can point at the same named in-memory H2 database (`DB_CLOSE_DELAY=-1`) and each re-runs `schema.sql` on its own `DataSource` initialization.
- Added ~46 tests across 13 test classes under `common/mail`, `notification/domain`, `notification/application`, `notification/infrastructure`, plus `notification/MailOutboxWiringIT.java`, and 4 hand-written test doubles (`FakeOutboxRepository`, `FakeMailTransport`, `FakeMailTemplateRenderer`, `FakeJavaMailSender` — no mocking framework, matching project convention). Notably: `RetryPolicyTests` proves the exact backoff schedule and exhaustion boundary; `OutboxMessageTests` proves the terminal-state variable wipe; `MailDispatchWorkerTests` attaches a Logback `ListAppender` to `MailDispatchWorker`'s logger and asserts a raw template-variable value never appears in any emitted log line; `OutboxSchemaIT` (Testcontainers-or-local-Postgres, mirrors `IdentitySchemaIT`) proves the CHECK constraints, cascade delete, and both partial-index queries against a real migrated schema; `OutboxMessageRepositoryTests` (`@DataJpaTest`) proves the JSON converter round-trips and the due/cleanup queries against H2.
- `scripts/verify-flyway-postgres.sh` — bumped the expected product-table count from 6 to 7 after `V3`.
- `infra/compose/compose.local.yml` — added a `mailpit` service (`axllent/mailpit:v1.20.3`, SMTP `1025`, web UI `8025`, same private network and named-volume pattern as `postgres`); `infra/compose/.env.example` gained `LIFEOS_MAILPIT_SMTP_PORT`/`LIFEOS_MAILPIT_UI_PORT`; `infra/compose/tests/compose-local.test.mjs` gained a matching assertion block; `infra/compose/README.md` documents starting it and where to read captured mail.

## Known limitations or follow-ups

- **No caller enqueues mail yet.** `TransactionalMailPort`/`MailOutboxService` are built and tested but unused outside this ticket's own tests. LOS-0503 (signup) and LOS-0507 (password reset) wire `auth.application` to `common.mail.TransactionalMailPort` when they land; LOS-1404 (audit) is a plausible source of the "SECURITY_ALERT" kind's real callers.
- Bundled template copy/variable names (`displayName`, `verificationUrl`/`resetUrl`, `expiresInMinutes`, `eventDescription`, `occurredAt`) are illustrative placeholders, not reviewed product copy — LOS-0503/LOS-0507/LOS-1404 own the real wording and variable set when they call the renderer for real; `ResourceMailTemplateRenderer` itself is generic `{{key}}` substitution and doesn't care what the keys are.
- Real end-to-end delivery through Mailpit is unverified in this environment (Docker unavailable) — see Validation above.
- `provider_message_id` is whatever JavaMail assigns after send, not a real SMTP-provider-issued id (plain SMTP has none) — sufficient for local troubleshooting; revisit if a production SMTP provider's own message id becomes available and worth capturing instead.
- Local PostgreSQL 16.14 was used for the schema ITs and the flyway-verification script (Docker unavailable); re-verify against PostgreSQL 18.4 when Docker is available, consistent with the LOS-0216 gate note LOS-0501 already recorded.
- This environment also needed `LC_ALL=C` for `initdb`/`pg_ctl` to start (without it, `pg_ctl: could not start server` / "postmaster became multithreaded during startup") and `JAVA_HOME` pointed at a JDK 21 install for `scripts/verify-flyway-postgres.sh`'s own `java -jar` step (the environment's default `java` on `PATH` is JDK 17) — both pre-existing environment quirks, not caused by this ticket (the JDK one matches LOS-0502's own note about `spotlessApply`/`spotlessCheck`).
