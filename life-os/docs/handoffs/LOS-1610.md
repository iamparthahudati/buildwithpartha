## Completed behavior

- **Authored Monitoring and Alerting Specification (`life-os/docs/58-MONITORING-AND-ALERTING.md`)**:
  - Defined end-to-end observability architecture covering all ticket acceptance criteria: external uptime probe (Cloudflare-fronted `https://buildwithpartha.tech/life-os`), origin/API readiness (Spring Boot Actuator liveness and readiness probes), TLS certificate expiry alerting (< 14 days warning, < 3 days critical), 5xx error rate and API p95 latency alerts, authentication failure spike detection, DB connection pool saturation and PostgreSQL availability alerts, VPS system resource alerts (CPU, memory, disk), and job/mail/backup age monitoring.
  - Documented complete stack: Prometheus + Alertmanager + Blackbox Exporter + Node Exporter + postgres-exporter.
  - Defined network security boundaries (all monitoring services on private `monitoring-net`, no external port exposure).
  - Specified 17 named alert rules across 5 rule files with severity labels and runbook_url annotations.
  - Defined Alertmanager routing tree (critical → `owner-critical`, warning → `owner-warning`, with 2 inhibition rules to suppress downstream alerts when root cause fires).
  - Provided 15 actionable operational runbooks (§8.1–§8.15) with numbered step-by-step resolution actions.
  - Documented backup age metric architecture (`lifeos.backup.last_success_timestamp_seconds`) via `BackupStatusMetricsProvider`.

- **Created Prometheus Scrape Configuration (`life-os/infra/monitoring/prometheus/prometheus.yml`)**:
  - 6 scrape jobs: `lifeos-api` (Micrometer/Actuator), `blackbox-internal` (internal health probes), `blackbox-external` (public URL probes via Cloudflare), `blackbox-tls` (TLS certificate expiry), `node` (VPS host system), `postgres` (PostgreSQL statistics).
  - References 5 alert rule files; connects to Alertmanager on `alertmanager:9093`; 15-day retention configured.

- **Created 5 Prometheus Alert Rule Files (`life-os/infra/monitoring/prometheus/rules/`)**:
  - `rules/uptime.yml` — `UptimeProbeDown`, `ApiReadinessDown`, `TLSExpiryWarning`, `TLSExpiryCritical`.
  - `rules/api.yml` — `HighApi5xxErrorRate`, `HighApiLatency`, `AuthFailureSpike`.
  - `rules/database.yml` — `DbPoolSaturation`, `DbConnectionsDown`, `DbDiskHighUsage`.
  - `rules/system.yml` — `HostHighCpu`, `HostHighMemory`, `HostDiskPressure`, `HostDiskCritical`.
  - `rules/jobs.yml` — `BackupAgeExceeded`, `AppFilesBackupAgeExceeded`, `BackgroundJobDeadLetter`, `MailSendFailureSpike`.
  - Every rule includes: `for:` duration, `labels.severity` (`critical`/`warning`), `annotations.summary`, `annotations.description`, `annotations.runbook_url`.

- **Created Blackbox Exporter Configuration (`life-os/infra/monitoring/blackbox/blackbox.yml`)**:
  - `http_2xx_follow_redirects` — for public Cloudflare-fronted URL probes.
  - `http_2xx` — for direct internal container health endpoint probes.
  - `tls_connect` — TCP TLS probe for certificate expiry monitoring.

- **Created Alertmanager Configuration (`life-os/infra/monitoring/alertmanager/alertmanager.yml`)**:
  - Routing tree grouping by `alertname`, `severity`, `env`; 30s group wait, 4h repeat for warnings.
  - Routes: `critical` → `owner-critical` (1h repeat), `warning` → `owner-warning` (4h repeat).
  - 2 inhibition rules: `UptimeProbeDown` suppresses `HighApi5xxErrorRate`/`HighApiLatency`/`ApiReadinessDown`; `DbConnectionsDown` suppresses `DbPoolSaturation`/`DbDiskHighUsage`.
  - Credentials injected via environment variables (`ALERTMANAGER_SMTP_*`, `ALERTMANAGER_OWNER_EMAIL`) from `/etc/life-os/secrets/.env.monitoring` — no secrets in source control.

- **Implemented `BackupStatusMetricsProvider` (`apps/api/src/main/java/.../common/metrics/BackupStatusMetricsProvider.java`)**:
  - Implements Micrometer `MeterBinder`; registered as Spring `@Component`.
  - Registers two `Gauge` meters: `lifeos.backup.last_success_timestamp_seconds{backup_type="postgres"}` and `{backup_type="app_files"}`.
  - Reads `last_success_epoch` field from `/var/log/life-os/postgres-backup-status.json` and `/var/log/life-os/app-files-backup-status.json` written by `backup-postgres.sh` and `backup-app-files.sh` (LOS-1608, LOS-1609).
  - Returns `0.0` (safe default — alert fires immediately) when file is missing, `last_success_epoch` field is absent, or JSON is malformed.
  - Paths configurable via `lifeos.monitoring.backup.postgres-status-path` and `lifeos.monitoring.backup.app-files-status-path` properties.
  - Privacy: exposes only Unix epoch timestamps — no user data, credentials, or PII.

- **Created Monitoring Docker Compose Overlay (`life-os/infra/compose/compose.monitoring.yml`)**:
  - 5 services with pinned image versions: `prom/prometheus:v2.53.1`, `prom/alertmanager:v0.27.0`, `prom/blackbox-exporter:v0.25.0`, `prom/node-exporter:v1.8.2`, `prometheuscommunity/postgres-exporter:v0.16.0`.
  - All services: non-root users (`65534:65534`), `no-new-privileges:true`, `read_only: true`, no externally exposed ports.
  - Private `lifeos-monitoring-net` network; attaches to existing `backend-net` and `db-net` as external networks for scrape access.
  - Persistent volumes: `lifeos-prometheus-data` (15-day retention, 4 GB cap), `lifeos-alertmanager-data`.
  - Usage: `docker compose -f compose.prod.yml -f compose.monitoring.yml up -d`.

- **Created Monitoring Secrets Template (`life-os/infra/monitoring/.env.monitoring.example`)**:
  - Documents all required secrets: SMTP host/username/password, owner email, `DATA_SOURCE_NAME` for postgres-exporter.
  - Includes setup guidance for the monitoring-only PostgreSQL read-only user (`pg_monitor` role).
  - Real values deployed to `/etc/life-os/secrets/.env.monitoring` on the VPS — never committed to source control.

- **Created Unit Test Suite (`BackupStatusMetricsProviderTests.java` — 7 scenarios)**:
  - Gauge registration for both backup types (correct metric name, backup_type tags).
  - Correct epoch timestamp from valid JSON.
  - `0.0` safe default when file does not exist.
  - `0.0` when `last_success_epoch` field is absent.
  - `0.0` graceful degradation on malformed JSON.
  - Privacy assertion: `backup_type` tag values are only `postgres` or `app_files` (no PII).
  - Float epoch value parsing.

## Database/config/deployment changes

- **No database schema changes** — monitoring is infrastructure-only and does not modify the LifeOS application database.
- **New monitoring compose overlay** (`compose.monitoring.yml`) to be deployed alongside `compose.prod.yml` in production.
- **New secrets file** required on VPS: `/etc/life-os/secrets/.env.monitoring` — populate from `infra/monitoring/.env.monitoring.example`. Requires:
  - SMTP credentials for Alertmanager alert delivery.
  - `ALERTMANAGER_OWNER_EMAIL` — owner notification address.
  - `DATA_SOURCE_NAME` — PostgreSQL connection string for monitoring-only read-only user (`lifeos_monitor`).
  - PostgreSQL setup: `CREATE USER lifeos_monitor WITH PASSWORD '...'; GRANT pg_monitor TO lifeos_monitor;`
- **Backup status JSON files** written by `backup-postgres.sh` and `backup-app-files.sh` must include the `last_success_epoch` Unix timestamp field (already documented in LOS-1608/LOS-1609 status JSON schema).

## Known limitations or follow-ups

- **No Grafana dashboards** in this ticket — ad-hoc visibility via Prometheus expression browser. Grafana is a post-launch enhancement.
- **No PagerDuty/OpsGenie integration** — Alertmanager email receiver is the initial delivery channel. Webhook integration is a follow-up.
- **External probe covers Cloudflare layer only** — `ApiReadinessDown` (internal readiness probe) provides the complementary origin-level coverage gap.
- **15-day Prometheus retention** — long-term trending requires a remote write target (out of scope for v1).
- **Centralized safe log integration** will be completed in **LOS-1611**.
