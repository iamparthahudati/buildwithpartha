## Completed behavior

Adds the Toast system: `state/ToastProvider.tsx` (queue) + `state/toastQueue.ts` (context/`useToast` hook) own the data; `components/feedback/Toast.tsx` (one entry) + `ToastViewport.tsx` (the mounted stack) render it. This is the first ticket to populate `state/`, which had stood as a placeholder (`export {};`) since `STRUCTURE.md` reserved it for exactly this — "minimal global ephemeral state" is what a cross-app toast queue is.

`Toast` composes `Alert` (LOS-0408) rather than drawing its own box: a toast is an `Alert` plus timing, not a different visual language. Unlike a general `Alert`, whose `announce` role is deliberately left for the caller to decide, a toast is *always* a fresh reaction to something that just happened — nobody renders one as static page content, which is what `Alert` itself is for — so `Toast` hard-codes the tone-to-announcement mapping (info/success polite, warning/danger assertive) internally. This is a narrower, unambiguous context than `Alert`'s own, so fixing the mapping here does not repeat the reasoning LOS-0408 gave for leaving it open.

### Pause without losing the remaining time

`hooks/useAutoDismissTimer.ts` is a new, toast-independent hook: WCAG 2.2.1 requires that non-essential timing can be paused, and a *correct* pause has to remember how much time had already elapsed, not just stop and later restart a full-length timer. It tracks the remainder explicitly across pause/resume, and separately exposes a `resetToken` — a refreshed toast needs a full restart even when its duration is unchanged (still 6 seconds), which comparing `durationMs` alone would miss.

Composing that hook inside `Toast` surfaced one more real interaction: the hook's reset always calls `resume()`, which is wrong if the pointer or focus never actually left the toast while a refresh arrived. `Toast` tracks its own paused state in a ref and, in an effect keyed to the same reset token, corrects the resumption back to paused when that is the case — tested directly (`stays paused through a refresh that arrives while the pointer is still on it`) rather than left as a plausible-sounding claim.

### Dedupe is the id, not a separate concept

`push` computes `id = options.id ?? `${tone}:${message}`` and reuses it as the queue entry's own id — there is no separate "dedupe key" alongside a random instance id, because "what makes two pushes the same toast" and "what identifies this toast for dismissal" are the same question. A second push with a matching id replaces the existing entry in place (same slot, refreshed content and countdown) instead of stacking a duplicate.

### "Queued" is a real cap, not just a stack

`ToastProvider`'s `maxVisible` (default 3) is the literal word in the ticket's name: past that many at once, a new toast waits in `pending` and is promoted — oldest-waiting first — the moment a visible slot is freed by a dismissal.

## Known limitations or follow-ups

- Not wired into `App.tsx`/`main.tsx`. The current app shell is LOS-0201's temporary readiness view, not a real composition root — mounting `ToastProvider`/`ToastViewport` belongs to whichever Epic 06 ticket first builds the real shell, not this one.
- No exit animation, only an entrance fade/slide — the same simplification `Tooltip` (LOS-0326) already made for the same reason: an exit animation needs a "still rendering while leaving" state this ticket did not need to add to get a correct, tested pause/resume/queue system shipped.
- `.lifeos-field__error`-style spans elsewhere in the product were not retrofitted onto `InlineMessage`, and this ticket does not change that; noted already in LOS-0408's handoff.
- Toast duration is a flat default (6000ms) rather than scaled to message length; `durationMs` is always overridable per push for a screen that needs otherwise.
