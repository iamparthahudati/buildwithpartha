## Completed behavior

Adds `SearchField` and its `useSearchField` hook to `apps/web/src/components/forms/`, composing `TextInput` with the six things a search box needs beyond a plain text field: debounced/submit timing, IME safety, a clear action, a focus shortcut, a loading announcement and a recent-searches/no-results panel.

### `useSearchField` owns the timing, not the value

`value` stays caller-controlled, exactly like every other LifeOS field. The hook only decides **when** to call `onSearch` for whatever value already exists:

- `debounced` mode (default) restarts a quiet-period timer on every keystroke and fires once typing pauses; `submit` mode never fires on its own.
- Enter always fires immediately and cancels any pending debounce, in either mode.
- IME composition is tracked through `onCompositionStart`/`onCompositionEnd`. A composing input method reports intermediate, not-yet-real characters through `value` on every keystroke; searching one of those would be searching for text the user never actually typed. The hook holds off scheduling while `composingRef.current` is true and picks the search back up on the one committed value change that follows `compositionend` — nothing is lost, only correctly delayed.
- Unmounting mid-debounce cancels the pending timer rather than firing into a component that no longer exists.

Kept as its own hook rather than inlined in the component so the timing logic is testable with fake timers independent of any markup, and reusable by a future control that wants the same behaviour with different visuals — a command palette's search field (LOS-0426) is the obvious candidate.

### The three accessibility traps a naive `suffix`/`loading` implementation would hit

`TextInput`'s `prefix`/`suffix` slots are `aria-hidden` decoration (correctly, for a static icon or unit). Three things could not go there without breaking:

1. An interactive submit button — `aria-hidden` hides a focusable element from the accessibility tree without removing its tab stop, leaving a control a screen-reader user can tab to but never hears announced. `SearchField` has no dedicated submit button for this reason; Enter already submits and is fully keyboard accessible.
2. The full `Spinner` component — it carries its own `role="status"` region, which an `aria-hidden` ancestor would swallow along with everything else inside it. The visible spinning icon in the `prefix` slot is therefore a bare decorative `Icon`, not `Spinner`; the actual waiting announcement lives in a genuine sibling `LiveRegion`, decoupled from the decorative icon entirely.
3. The shortcut-key badge (`kbd`) is fine as decoration: Tab already reaches the field for every keyboard user, so the hint is a bonus rather than the only way in, matching the tone guide's rule against tooltip-only instructions.

### Shortcut key

`shortcutKey` (e.g. `"/"`) registers a single document-level `keydown` listener that focuses the field, skipped entirely when a modifier key is held or when `document.activeElement` is already an editable element — typing `/` into a different field must never steal focus away from it, and the check covers native inputs, textareas, selects and `contenteditable` elements.

### Recent searches and no results

A small panel, not a full listbox — `Combobox` (LOS-0403) is where keyboard-navigable, roving-focus suggestions belong. Recent searches show only while the field is focused with an empty value (a proposal, dismissed on blur via a focus-within check that ignores blur events landing on a child button); the no-results message stays independent of focus once `resultCount === 0` for a non-empty value, since it is information the user should still be able to read after looking away. `resultCount === undefined` (the state before any search has completed) shows nothing, rather than guessing.

## Known limitations or follow-ups

- The recent-searches and no-results panel does not implement `aria-expanded`/`combobox` semantics; it is a plain focus-shown panel with ordinary tab order through its buttons, not a listbox. This is deliberate scope: full roving-focus suggestion semantics are `Combobox`'s job (LOS-0403).
- `shortcutKey` supports exactly one unmodified character key. A multi-key chord (e.g. `Cmd+K`) is out of scope here and belongs to `CommandPalette` (LOS-0426), which is expected to compose its own shortcut handling rather than reuse this one.
- No feature yet wires `SearchField` to a real API, so `loading`/`resultCount`/`recentSearches` are exercised only by the catalog's local state in this ticket.
